Chat formatting

Use one formatter to control player names, rank prefixes, colors, and message layout.

EssentialsX Chat

Used for: Group-based chat formats, prefixes, suffixes, and colors in the EssentialsX suite.

How CoreChatX replaces this use: CoreChatX can take over public-chat formatting through chat.yml, LuckPerms rank prefixes, primary-group formats, and optional PlaceholderAPI values. Channel-specific formats live in channels.yml.

Scope and differences: This replaces the chat-formatting role. Keep EssentialsX if you use its homes, warps, economy, kits, or other commands. Recreate formats with CoreChatX placeholders; the EssentialsX Chat configuration is not imported.

LPC / LuckPermsChat

Used for: Chat formatting with LuckPerms prefixes, group formats, RGB colors, and PlaceholderAPI support.

How CoreChatX replaces this use: CoreChatX can replace this formatter using public-chat.format and public-chat.group-formats in chat.yml. It reads LuckPerms metadata and supports MiniMessage templates.

Scope and differences: LuckPerms stays installed to manage permissions and ranks. Rebuild LPC templates and check any world or server contexts you rely on; the two plugins do not share a configuration format.

DeluxeChat

Used for: Configurable chat formats with hover and click actions, placeholders, private messaging, and BungeeCord options.

How CoreChatX replaces this use: CoreChatX covers formatted public chat, MiniMessage hover/click actions, and /msg / /reply. Group and channel formats define the layout; network messages run through the CoreChatX Velocity setup.

Scope and differences: Convert formats manually. DeluxeChat format-priority permissions and recipient-dependent relational placeholders are not interchangeable with CoreChatX primary-group formatting. A BungeeCord installation must move to a supported Velocity setup for CoreChatX network chat.

ChatEx

Used for: Chat prefixes and suffixes, join/quit messages, word controls, chat clearing, and other chat-management features.

Channels and network chat

CoreChatX uses Paper for standalone servers and Paper plus Velocity for networks. Network channels and private messages stay inside the configured CoreChatX network group.

VentureChat

Used for: Public and private channels, local-distance chat, network channels, permissions, formatting, and moderation tools.

How CoreChatX replaces this use: CoreChatX can take over global, local, staff, and custom channels with separate send/receive permissions. Use NETWORK, SERVER, or LOCAL_RADIUS in channels.yml; private messages and social spy are included.

Scope and differences: CoreChatX uses a different channel and permission model. Its player mutes do not reproduce VentureChat's per-channel mute model, and /clearchat is not selective removal of individual messages. Rebuild channel access and use the supported Velocity topology.

ChatControl

Used for: Chat channels, formatting, moderation, and a broader rules system with custom actions and integrations.

Scope and differences: ChatControl's rule scripts, JavaScript variables, mail, and individual-message removal are not equivalent to CoreChatX features. Keep any required advanced rules covered before replacing it. CoreChatX's word filter censors configured terms and still sends the message.

What does replacing a feature look like?

These four independent examples show how to configure common uses after installing CoreChatX. Pick the ones you need; they are not a complete installation or migration procedure.

Back up every file in the plugin folder before editing. These are partial examples: edit or merge the shown keys into the generated files, keep unrelated settings, and never add a second channels: or keywords: root. Use spaces for YAML indentation.

On a network, apply the intended Paper settings to each participating backend and keep matching channel IDs. The Velocity setup and network groups must already be configured. For these examples, stop the affected server before editing, start it again afterward, and check the result with an ordinary player and a staff account.

1. Give global chat a consistent layout

A simple replacement for a chat-formatting module. This sets the global channel format directly, so a primary-group format in chat.yml will not override it.

File: plugins/CoreChatX/channels.yml on Paper. Edit the existing keys shown here.

channels:
  global:
    format: "{rank_prefix}<white>{player_nickname}</white><dark_gray> » </dark_gray>{message}"

Expected result: global messages show the LuckPerms rank prefix, player nickname, and message. Keep the LuckPerms hook enabled if you want that prefix. For different layouts by rank, leave the channel format empty and configure public-chat.group-formats in chat.yml instead. The order is channel format, primary-group format, then the general public-chat format.

2. Create a staff-only chat shortcut

An example for replacing a dedicated staff-chat channel. Use an unused shortcut name if another plugin already owns /sc.

File: plugins/CoreChatX/channels.yml on Paper. Edit the existing keys shown here.

channels:
  staff:
    enabled: true
    default: false
    shortcut: "sc"
    scope: "NETWORK"
    permission-send: "corechatx.channel.staff"
    permission-receive: "corechatx.staff"
    allow-chat-bubbles: false
    export-to-bridges: false
    format: "<red>[Staff]</red> {player_nickname}<dark_gray> » </dark_gray>{message}"

Access: grant staff the two configured permission nodes; review corechatx.staff because other CoreChatX features also use it. For a narrowly scoped custom chat, you can choose your own send/receive nodes instead. Also grant corechatx.command.channel for channel commands, including the shortcut.
Expected result: /sc selects staff chat, while /sc message sends one staff message without changing the active channel. Authorized staff in the same CoreChatX network group can receive it. This example disables outgoing bridge exports and overhead bubbles; do not configure a Discord inbound route to this channel unless you intend to provide that access too.

3. Turn a rules token into a clickable link

A small replacement for an interactive keyword feature. Replace the example URL with your real rules page; the token remains visible as ordinary text where keyword rendering is not available.

File: plugins/CoreChatX/keywords.yml on Paper. Edit the existing keys shown here.

keywords:
  rules:
    enabled: true
    tokens: ["[rules]"]
    renderer: "<yellow><hover:show_text:'<gray>Open the server rules</gray>'><click:open_url:'https://example.com/rules'>[Rules]</click></hover></yellow>"
    allow-placeholderapi: false
    permission: ""
    enabled-channels: []
    disabled-channels: []

Expected result: sending [rules] in supported CoreChatX chat produces a clickable [Rules] link with hover text. The empty permission allows all players; set a permission or channel allowlist if the token should be restricted. Minecraft may ask the player to confirm opening the link.

4. Keep overhead bubbles close to the player

A replacement for the nearby-player speech-bubble use case. This example keeps staff conversations out of bubbles and limits the visible distance.

File: plugins/CoreChatX/chatbubbles.yml on Paper. Edit the existing keys shown here.

enabled: true
default-enabled: true
permission: "corechatx.chatbubbles.use"
disabled-channels: ["staff"]
max-visible-distance: 24
max-line-length: 28
max-plain-length: 80
base-duration-ticks: 80
max-duration-ticks: 160

Expected result: eligible player messages create nearby overhead bubbles on that backend. Grant corechatx.chatbubbles.use, allow bubbles in the channel, and enable them in the player's /ccxsettings. default-enabled sets the default for a new preference; it does not overwrite a player's saved choice. Keep any other channel restrictions from your existing file.

Common replacement questions

Can I install CoreChatX alongside my existing chat plugin?

Retain other plugins for the functions you still need, but give each chat function one owner. Two formatters or Discord routes handling the same message can produce duplicate output or conflicting behavior. Follow the other plugin's documentation to disable overlapping modules and resolve shared command names before enabling the replacement.

Can I reuse my old YAML, permissions, and player data?

Use old files as a reference, not as CoreChatX configuration. Recreate templates and permissions with the CoreChatX reference. There is no automatic importer for the compared plugins' nicknames, ignores, mutes, or account links. Keep a complete backup and decide how each saved setting will be restored or recreated before switching.

Do I need MySQL, Redis, or a client mod?

CoreChatX uses YAML by default and offers MySQL as an optional storage backend. MySQL is not required just to use channels, previews, or the supported Velocity network setup. CoreChatX does not require Redis for its network transport or a client mod for its standard chat features. Supported Paper and Velocity versions still matter; follow the installation guide.

Can players choose which settings stay enabled?

/ccxsettings exposes player preferences such as private-message availability and chat bubbles. Players can choose whether their active channel persists or returns to the default after disconnecting, and can hide accessible channels with the relevant commands. Permissions and server configuration still control which features they may use; these preferences do not grant staff access.

Does replacing several plugins guarantee better performance?

No. A smaller plugin list does not by itself establish lower CPU, memory, or disk use. This page compares functions and configuration boundaries. Performance depends on the enabled features, traffic, integrations, and deployment; assess it on your own server.

Before switching plugins

  1. Back up every file in the affected plugin folders first. Back up any database that contains their saved data as well.
  2. List the features you use. Include formats, channels, commands, permissions, nicknames, mutes, ignores, account links, and any required integrations. Check the differences above against that list.
  3. Recreate the configuration on a separate test server. Follow the Paper or Velocity setup guide. Keep LuckPerms and the PlaceholderAPI expansions needed by your chosen formats. CoreChatX does not replace these providers.
  4. Give each feature one owner. Disable overlapping chat formatters, commands, token handlers, and Discord routes in the plugins you retain. Restart, then check chat delivery, permission restrictions, private messages, previews, and Discord forwarding before moving the setup to your server.

Saved data is a separate step. CoreChatX does not include an automatic importer for the plugins compared here. Its YAML-to-MySQL guide migrates existing CoreChatX data; it does not convert another plugin's nicknames, mutes, ignores, or Discord links.
