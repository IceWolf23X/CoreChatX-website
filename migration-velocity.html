Before anything else, back up every file in the CoreChatX plugin folder. Stop the affected servers normally and copy plugins/corechatx/ on Velocity, including all of data/groups/, and plugins/CoreChatX/ on every Paper server to a separate location, including every subfolder. Keep the old JARs. The first step below explains this backup; do it before replacing JARs, editing configuration, or running migration commands.

2026.2.6 YAML → 2026.3.0 MySQL · Velocity network

Velocity network: migrate from YAML to MySQL.

This page is the complete procedure for CoreChatX running on a Velocity proxy with Paper servers in PROXY mode, even if there is only one Paper server. Follow the numbered steps in order, from 1 to 15. All required instructions are on this page. A step is complete only when its “Continue when” condition is satisfied.

This moves existing CoreChatX data from 2026.2.6 YAML to 2026.3.0 MySQL. Updating the plugin does not require MySQL; YAML remains supported. The migration includes player preferences, nicknames, statistics, channels, ignores, mutes, global state, and Discord linking data. Configuration files, worlds, and other plugins are not moved into MySQL.

1. Stop the servers and back up the whole plugin folder

Server state: stop the servers normally, then wait until every process has finished.

Block normal player connections using your hosting panel, maintenance controls, or firewall. Prevent Discord and other integrations or scheduled commands from changing CoreChatX data during the procedure.

Copy every file and subfolder from plugins/corechatx/ on Velocity, including all of data/groups/, and plugins/CoreChatX/ on every Paper server to a separate backup location. Include configuration, player data, credentials, journals, existing backups, and rollback folders. Keep the old 2026.2.6 JARs separately.

Open the backup location and check that the copy is complete. Keep this original copy until the migration has been checked and you no longer need it for recovery.

Do not rename the encoded folders inside data/groups/, select only one group, or copy the Paper files over the proxy data. Velocity owns the shared player data.

Continue when: the servers are stopped, normal access is blocked, and you have verified the complete folder copies.

2. Get an empty MySQL database and its connection details

Server state: Velocity and all participating Paper servers are stopped.

In your hosting panel, create an empty database and a dedicated database user, or ask your host/database administrator to do it. CoreChatX creates its tables, but does not install MySQL or create the database or user.

  • Write down the database hostname, port, database name, username, and password. These are not your Minecraft server address or Minecraft account login.
  • Allow the user to connect from the machine running Velocity, read/write the CoreChatX data, and create/alter the required tables and indexes.
  • Obtain the database hostname and certificate setup needed for verified TLS. Keep enough free disk space for backups.

For a rehearsal, use a separate copy of your installation and a separate database, with ordinary players and live integration traffic disconnected. Never point the copy at the same live storage identity.

Continue when: the empty database and user are ready, and you have the hostname, port, database name, username, and password.

3. Replace the CoreChatX JARs

Server state: Velocity and all participating Paper servers are stopped.

Download the 2026.3.0 Velocity JAR for the proxy and the 2026.3.0 Paper JAR for every participating Paper server. Use the CoreChatX downloads.

  • Move the old CoreChatX JAR out of the live plugins/ directory into your backup location. Install the new platform-specific JAR so only one CoreChatX JAR remains per server.
  • Leave every configuration and player-data file in place. Do not delete the plugin folder to generate a fresh installation.
  • Keep your current Minecraft version and deployment configuration. This procedure updates CoreChatX and its storage.

Update the entire participating network together. CoreChatX 2026.3.0 uses protocol 29; do not mix it with older Paper or Velocity plugin builds. Keep every Paper server in PROXY mode and preserve group assignments.

Continue when: all required 2026.3.0 JARs are installed and the servers are still stopped.

4. Start Velocity with YAML and check the existing installation

Server state: start only Velocity; leave all Paper servers stopped and player access blocked.

If plugins/corechatx/velocity-storage.yml already exists, leave storage.backend set to YAML. If the file does not exist yet, 2026.3.0 generates it with YAML selected. Wait for startup to finish.

Open the Velocity server console in your hosting panel or server terminal. All commands in this guide go in that console, without a leading slash. They are not commands for Minecraft chat, Windows PowerShell, or a Linux shell. Run one command at a time and wait for its response.

ccxstorage status

Look for backend=YAML, all listed groups OPEN, and transitions=none. OPEN means CoreChatX data operations are available; it does not unblock player connections.

The scopes list contains your CoreChatX groups from network-channel in plugins/corechatx/velocity-config.properties. A group such as corechatx:main can contain several Paper servers. It is not a chat channel such as global/staff. Check that every existing group is listed and leave the group configuration unchanged.

If startup reports malformed files, unexpected empty data, or an unfinished transition, stop the procedure and resolve that problem. Do not select MYSQL to bypass it.

Continue when: Velocity has started successfully and the status shows the expected YAML installation.

5. Stop Velocity and fill in the database connection

Server state: stop Velocity normally before editing. Paper servers remain stopped.

Open plugins/corechatx/velocity-storage.yml. Edit the existing keys shown below. This is a partial example: keep the rest of the generated file, its timeout/pool settings, and one single storage: section. Use spaces for YAML indentation.

storage:
  backend: "YAML"
  namespace: "production"
  mysql:
    host: "db.example.net"
    port: 3306
    database: "corechatx"
    username: "corechatx"
    password: 'REPLACE_WITH_YOUR_DATABASE_PASSWORD'
    password-env: ""
    ssl-mode: "VERIFY_IDENTITY"
    schema-auto-migrate: true
  • Keep backend: "YAML". The database connection can be configured while CoreChatX still reads the YAML files. Selecting MYSQL alone does not copy your old data.
  • Keep your existing namespace. These labels identify the dataset. The example uses the defaults; do not overwrite custom values.
  • Replace host, port, database, and username with the details you obtained. db.example.net is only an example. 127.0.0.1 works only if MySQL is reachable there from the Java process.
  • Replace the example password with the real database password and leave password-env: "" for this method. Keep the quotes. A single quote inside a YAML single-quoted password is written twice. Keep the file and its backups private.
  • Keep ssl-mode: "VERIFY_IDENTITY" and configure any Java certificate trust required by your host. Keep schema-auto-migrate: true so CoreChatX can prepare its tables. This does not import your player data.
Optional: use an existing hosting-panel password variable instead

If your panel/service already supplies environment variables to the Java process running Velocity, set CORECHATX_MYSQL_PASSWORD there to the database password. In the same storage.mysql section, use:

    password: ""
    password-env: "CORECHATX_MYSQL_PASSWORD"

A nonblank value of the named variable overrides the inline password. The Java process must inherit that variable when it starts. Choose either this method or the inline method above.

Save the file. If your administrator requires schema-auto-migrate: false, they must arrange the required CoreChatX schema before you continue; an incomplete schema is rejected.

Continue when: the file is saved with your connection details, backend: "YAML", and Velocity still stopped.

6. Start Velocity again and check the YAML source

Server state: start only Velocity; keep Paper stopped and player access blocked.

Use a full server start, not /corechatx reload: storage settings are read at startup. Wait for startup to finish, then run:

ccxstorage status

Confirm backend=YAML, all listed groups OPEN, and transitions=none. Then check the source files:

ccxstorage check files --all-scopes

Expect one result per group, with sha256 and counts. Counts summarize saved records. SHA-256 is a fingerprint of their contents; the plugin calculates it for you. Save this output. Unexpectedly missing player data must be investigated before importing.

--all-scopes means every configured CoreChatX group. Use it even if your proxy has only one group. Velocity has one backend setting, so the storage switch must include all groups.

Continue when: the YAML files validate successfully and contain the expected data.

7. Check the MySQL connection

Server state: Velocity is running; all Paper servers remain stopped; normal player access is blocked.

In the same Velocity console, run:

ccxstorage check mysql --all-scopes

Expect a database result for each group, with a fingerprint and counts, and no error. The database has not received your YAML player data yet, so its counts do not need to match the source at this point.

This check may create CoreChatX tables when automatic schema migration is enabled. Tables appearing in MySQL do not mean your players have been migrated. The import has not run yet.

If this reports connection, password, certificate, permission, or schema errors, stop here. Correct the reported cause. If you edit the storage file or process environment, stop/start Velocity and repeat the checks before continuing. Never erase existing database data to make a check pass.

Continue when: the MySQL check succeeds without errors for your configured database.

8. Create and verify a CoreChatX data backup

Server state: Velocity is running; all Paper servers remain stopped; normal player access is blocked.

ccxstorage backup files --all-scopes

The command returns one archive for each group. Save the output containing backup=, sha256=, and archive=. Keep the archive at the reported location.

Copy the value immediately after backup=, stopping before the next comma. Replace <backup-id> below with that value. Do not include the label, brackets, commas, or a full filesystem path:

ccxstorage backup verify <backup-id>

Repeat verification for every returned backup ID. Success prints the backup ID, fingerprint, and archive location again. If you lost an ID, ccxstorage backup list lists archive filenames, which this command also accepts.

This archive contains CoreChatX data, but excludes credentials and storage configuration. Keep the original complete plugin-folder backup too.

Continue when: every new backup has verified successfully and its archive has been kept.

9. Create the migration plan

Server state: Velocity is running; all Paper servers remain stopped; normal player access is blocked.

ccxstorage migrate files-to-mysql plan --all-scopes

The result has one line per group. Save each line and keep its scope, run, and confirmation-token together. The scope is the exact group name to use in the command; do not substitute a Paper server name.

Planning records the proposed operation and checks its source and destination. It does not copy player data yet. The confirmation token is not your database password.

The token expires after 10 minutes. Keep player and integration traffic blocked, do not edit data or configuration, and proceed directly to execution. If the token expires, is lost, or the source changes, stop and inspect the run before creating another plan.

Continue when: the plan succeeds and you have the fresh confirmation values for all groups.

10. Execute the plan and wait for the import to finish

Server state: Velocity is running; all Paper servers remain stopped; normal player access is blocked.

Build one execute command. For each plan, join the three actual values with equals signs: group-name=run-id=token. Put one such entry for every group on the same line, separated by spaces.

For a proxy whose only group is corechatx:main, the template is:

ccxstorage migrate files-to-mysql execute --all-scopes corechatx:main=<run-uuid>=<confirmation-token>

Worked example, with invented values: if your two plans contained these fields:

scope=corechatx:survival, run=11111111-1111-4111-8111-111111111111, confirmation-token=EXAMPLE_SURVIVAL
scope=corechatx:creative, run=22222222-2222-4222-8222-222222222222, confirmation-token=EXAMPLE_CREATIVE

Their assembled command would be:

ccxstorage migrate files-to-mysql execute --all-scopes corechatx:survival=11111111-1111-4111-8111-111111111111=EXAMPLE_SURVIVAL corechatx:creative=22222222-2222-4222-8222-222222222222=EXAMPLE_CREATIVE

Use your real values and group list. Do not paste the invented values. Include every group exactly once, with no brackets, quotes, or commas. Three Paper servers in one group still require only one group entry. Run only your assembled command, not both examples.

Wait for the final response. CoreChatX pauses data changes, saves pending YAML writes, checks that the source still matches the plan and the destination is empty, imports the data, and verifies it. Keep every source file, backup, and journal.

The successful result says All Velocity scopes verified. YAML remains frozen. Change storage.backend to MYSQL and restart. Here, frozen means CoreChatX has paused new data changes while activation is pending. Leave the backend on YAML while you perform the immediate verification below.

Continue when: the final response confirms all groups are verified. Keep YAML selected for the next check.

11. Verify the imported data before activation

Server state: Velocity is running; all Paper servers remain stopped; normal player access is blocked. YAML data changes are now paused.

ccxstorage migrate files-to-mysql status --all-scopes

Find every new run ID from the plan. Each must show state=VERIFIED_PENDING_CUTOVER. This means the copy is verified and waiting to be activated.

Now verify all groups together:

ccxstorage check parity --all-scopes

Expect Parity verified for all Velocity migration scopes. Parity checks that the saved migration contents match. If verification fails, leave player access blocked, preserve all files, and resolve the error instead of selecting MYSQL.

Continue when: both the migration status and the parity check confirm success.

12. Stop Velocity, select MYSQL, and start it again

Server state: stop Velocity normally now. Leave Paper servers stopped.

The import and verification have succeeded. You can now make MySQL the storage used by the plugin.

  • Open plugins/corechatx/velocity-storage.yml.
  • Under the existing storage: section, change the single line backend: "YAML" to backend: "MYSQL".
  • Save the file. Do not change the database, password, namespace, scope/group configuration, or any other setting. Do not delete YAML or journal files.
  • Start Velocity again with MySQL reachable and player access still blocked. Wait for CoreChatX startup to finish.

If startup fails, do not change back to YAML as a shortcut. CoreChatX intentionally keeps storage-dependent features unavailable when MySQL cannot start. Correct the reported connection, schema, ownership, or recovery problem.

Continue when: Velocity has finished starting with MYSQL selected and no storage startup error.

13. Confirm that MySQL is active

Server state: Velocity is running; all Paper servers remain stopped; normal player access is blocked.

ccxstorage status

Expect backend=MYSQL, all listed groups OPEN, and transitions=none. No unfinished transition should remain.

ccxstorage check mysql --all-scopes

Confirm that database access succeeds for every group.

ccxstorage migrate files-to-mysql status --all-scopes

Find the new migration runs. Each should now show state=ACTIVE.

Continue when: the selected backend is MYSQL, database checks pass, and every new run is ACTIVE.

14. Check player data and one new saved change

Server state: Velocity is running; normal player access remains blocked.

Start the updated Paper servers now. Keep their existing PROXY mode and group assignments. Do not change their local storage backend to MYSQL: the database connection belongs to Velocity.

Allow only the players you need for these checks. Keep ordinary access blocked. Compare existing nicknames, language/settings, selected and hidden channels, ignores, mutes, Discord links, and global chat state with the values from your backup.

  • Open /ccxsettings with a checking player. Change a harmless notification preference and wait for the success message.
  • Disconnect and reconnect that player. Confirm the preference was kept.
  • Disconnect the checking players, stop Velocity normally, and start it again with MYSQL still selected. Reconnect and confirm the new preference still has the saved value.
  • Check public chat, private messages, permissions, moderation, and the integrations you use. Restore integration traffic only as needed for your checks.

Repeat the checks in every group. Check cross-server messages and transfers between Paper servers in the same group, and separation between different groups.

If a value is missing or a feature behaves incorrectly, keep ordinary access blocked and investigate. Keep all source files and archives.

Continue when: the existing data is correct, the new preference survives reconnect and restart, and the enabled features work.

15. Make a current backup and reopen player access

Server state: Velocity and its Paper servers are running; only your checking players can connect.

In the Velocity console, create a backup of the current MySQL data:

ccxstorage backup mysql --all-scopes

For each returned archive, copy the value after backup= and verify it:

ccxstorage backup verify <backup-id>

After successful verification, keep the archive, restore normal player access, and restore the integration traffic you paused. Keep the complete original folder backup too.

New CoreChatX player data now goes into MySQL. The old YAML data files are not an updated mirror; do not edit them expecting live changes or overwrite newer data with the original backup. Configuration files still stay in the plugin folder.

backup mysql contains CoreChatX data, so retain your regular database backup policy as well. check parity was for the unfinished migration and is not a routine comparison against old YAML after activation.

Continue when: the migration is complete. The server can remain open on MySQL. There are no further migration steps.

Optional recovery and rollback

A successful migration ends at step 15. Read these references only if an operation failed or you later decide to return to YAML.

Optional: return this Velocity installation to YAML

This is optional, after a completed migration. Use it only if you later want to return to YAML while keeping CoreChatX 2026.3.0. It exports the latest MySQL data; restoring the original YAML backup instead would discard newer changes.

Block player and integration changes again. Make current backups. Keep Velocity running on MYSQL with the database reachable. Stop all Paper servers.

ccxstorage rollback mysql-to-files plan --all-scopes

Copy the new rollback run IDs and confirmation tokens. They expire after 10 minutes. Do not reuse the old forward-migration values.

Use one group=run=token entry per configured group, all on one command line. Replace the placeholders and omit square/angle brackets and the example ellipsis. For a single corechatx:main group:

ccxstorage rollback mysql-to-files execute --all-scopes corechatx:main=<rollback-run-uuid>=<rollback-token>

For every additional group, append its own group=run=token entry separated by a space. Include all groups exactly once.

Wait for successful staging and the instruction to select YAML and restart. Then run these two checks separately:

ccxstorage rollback mysql-to-files status --all-scopes
ccxstorage check parity --all-scopes
  • Only after success, stop Velocity, open plugins/corechatx/velocity-storage.yml, and change only backend: "MYSQL" to backend: "YAML".
  • Start Velocity again. Keep MySQL reachable because startup still needs to verify the rollback. Preserve all journals and staging folders.
  • Run ccxstorage status. Expect YAML, storage operations OPEN, and no unfinished transition.
  • Run ccxstorage check files --all-scopes. Start the Paper servers, then check saved player data.
  • Make a fresh ccxstorage backup files --all-scopes, verify every returned backup ID, then reopen access.

Former files are kept under storage-rollbacks/<run>-originals. Do not delete the database before rollback activation has finished. Downgrading the JAR to 2026.2.6 is a different operation requiring a separately planned full restoration and a decision about newer data it could lose.

If an operation fails: Velocity recovery reference

On any failure, pause the walkthrough. Keep ordinary access blocked and preserve the entire plugin folder, backups, journals, staging files, and console output. CoreChatX can pause storage changes while its network port still accepts connections; keep your own access restriction in place.

Read the state in the Velocity console. These commands inspect it:

ccxstorage status
ccxstorage history --all-scopes
ccxstorage migrate files-to-mysql status --all-scopes
  • For a connection, authentication, certificate, or schema error, correct the reported setup problem. Restart after editing storage settings and repeat the relevant check.
  • For an expired/lost token or changed source, inspect the existing run. Cancel it safely before making a fresh plan; a partially executed run needs recovery, not a blind second import.
  • For an interrupted import, start the same installation with its files and identity unchanged, read status/history, and resume only when the saved state supports it.
  • For a nonempty target or another active owner, keep existing data. Resolve the database/ownership choice instead of forcing an import or deleting tables.

The following are alternatives, not a script. Resume continues a supported unfinished migration. Abort cancels only when CoreChatX can verify that doing so is safe. The brackets mark optional arguments and are not typed:

ccxstorage migrate files-to-mysql resume --all-scopes [<group>=<token> ...]
ccxstorage migrate files-to-mysql abort --all-scopes

For an unfinished rollback, use the matching rollback commands instead:

ccxstorage rollback mysql-to-files status --all-scopes
ccxstorage rollback mysql-to-files resume --all-scopes [<group>=<token> ...]
ccxstorage rollback mysql-to-files abort --all-scopes

Follow the command response, including any required restart after abort/recovery. A verified abort allows a fresh plan with new values without deleting the old journal. After MySQL is ACTIVE, returning to YAML uses a new rollback plan, not abort of the completed migration.

Do not delete journals, edit frozen YAML, truncate database tables, change namespace/groups, or alter checksums to bypass an error. If another process took the database lease, resolve that conflict and restart the intended owner. Keep the corrected 2026.3.0 JARs: older builds cannot read the newer ABORTED journal state.
