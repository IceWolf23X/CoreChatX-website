Before anything else, back up every file in the CoreChatX plugin folder. Stop the affected servers gracefully, then copy the entire folder, including every file and subfolder, to a separate backup location before replacing JARs, editing configuration, or running migration commands.

On Paper, back up plugins/CoreChatX/. On a Velocity network, also back up plugins/corechatx/ on the proxy, including all of data/groups/, and the CoreChatX folder on every Paper backend. Include configuration, player data, credentials, journals, and existing backups. Verify that the copy is complete before continuing.

Migrate your YAML data to MySQL.

Understand the order before running commands.

Updating CoreChatX does not require MySQL. You can use 2026.3.0 with YAML. Follow this guide only if you also want to move existing CoreChatX player data from files into a MySQL database.

The migration changes where CoreChatX saves player preferences, nicknames, channels, ignores, mutes, statistics, and Discord linking data. Your configuration files stay in the plugin folder. Minecraft worlds and data belonging to other plugins are outside this migration.

  1. Prepare and back up. Stop player access, copy the plugin folders, and obtain the database details.
  2. Update the JARs. Start 2026.3.0 using your existing YAML data.
  3. Configure the connection. Keep backend: "YAML" while you prepare to import.
  4. Run the Paper or Velocity migration commands. CoreChatX pauses data changes, copies the data, and verifies it.
  5. Activate MySQL when instructed. Stop the server, change backend to "MYSQL", and start it again.
  6. Verify and reopen. Check the old data and a new saved change before allowing normal access.

Why not select MYSQL immediately? That setting selects which storage to use; it does not copy your old data. The copy must succeed before you change the setting.

Choose the instructions for your installation

Standalone Paper

Players connect directly to Paper and CoreChatX uses STANDALONE mode. Run commands in that Paper server's console and edit plugins/CoreChatX/storage.yml.

Follow steps 1–3, step 4A, then steps 5–6. Skip 4B.

Velocity network

Players connect through Velocity and CoreChatX on Paper uses PROXY mode. Run commands in the Velocity console and edit plugins/corechatx/velocity-storage.yml.

Follow steps 1–3, step 4B, then steps 5–6. Skip 4A, even if the proxy has only one Paper server.

On a network, Velocity stores the shared data. Do not import the Paper backends' local files or configure MySQL separately on each backend. Keep the same deployment mode and network groups throughout this procedure.

Try the procedure on an isolated copy of your own installation first. Give that copy a separate database and prevent it from receiving normal players or live integration traffic. Rehearse migration and returning to YAML, then compare saved player values. Keep the complete backup from the start of this page.

What do the terms in the console mean?
Backend
In the storage configuration, this means YAML or MYSQL. A Paper backend server behind Velocity is a different use of the same word.
Namespace and scope
Labels that identify which installation's data CoreChatX should read. Leave the generated values unchanged for a new default setup; keep existing custom values. Changing them can select a different dataset.
Velocity group / scope
A group from network-channel in velocity-config.properties, such as corechatx:main. Several Paper servers can share one group. It is not a chat channel such as global or staff.
Run and confirmation token
The plan prints an ID for this operation and a temporary confirmation value. Copy both into the execute command. They are not your database password.
Counts, sha256, and parity
Counts summarize saved records; SHA-256 is a fingerprint of their contents. A parity check verifies that the migration's saved contents match. You do not calculate these values yourself.
Frozen data / open transition
CoreChatX has paused data changes while a migration or rollback is unfinished. Follow its activation or recovery instruction before allowing players back.

1. Prepare and back up

Stop player access and make a complete copy.

Server state for the backup: stopped. On a network, stop Velocity and all participating Paper servers. Use a normal shutdown and wait for each process to finish.

  1. Schedule downtime. Block ordinary player connections using your hosting panel, maintenance controls, or firewall, and keep them blocked until step 6. Prevent Discord, scheduled commands, and other integrations from changing CoreChatX data during the procedure.
  2. Copy the entire CoreChatX plugin folder to a separate backup location. Standalone: plugins/CoreChatX/. Network: plugins/corechatx/ on Velocity and plugins/CoreChatX/ on every Paper server. Keep the old JARs separately too.
  3. Check that the copy includes all files and subfolders. On Velocity, this includes all of data/groups/; do not rename its folders or copy only one group. Keep existing backup, journal, and rollback folders.
  4. Write down a few existing player values you can compare later: nickname, selected channel, settings, ignores, mutes, and Discord link. On Velocity, choose players from every configured group.

Have the database details ready

Create an empty, dedicated MySQL database and a database user through your hosting panel or database administrator. CoreChatX creates its own tables, but it does not install MySQL, create a database user, or create the database itself.

  • Obtain the database host, port, database name, username, and password. These are database connection details, not your Minecraft server address or account login.
  • The database user must be allowed to connect from the machine running standalone Paper or Velocity, read and write the data, and create/alter the CoreChatX tables and indexes.
  • The secure default checks the database certificate and hostname. Obtain the correct TLS hostname and any certificate trust setup from your host. Also check space for backups and access to the correct server console.

The built-in backup in step 4 is an additional archive of CoreChatX data. It excludes credentials and storage configuration, so it does not replace your complete folder copy.

Continue when: the complete backup is available, player access is blocked, and the database details are ready.

2. Update CoreChatX while keeping YAML

Let 2026.3.0 load the existing files first.

  1. With the servers stopped, replace the JARs. Put the 2026.3.0 Paper JAR on Paper and the Velocity JAR on Velocity. Move old JARs out of the live plugins/ directories so only one CoreChatX JAR remains per server. Keep configuration and player files in place.
  2. Start standalone Paper, or start only Velocity. Keep player access blocked. Leave network Paper servers stopped until step 5. If a storage file already exists, keep storage.backend set to YAML. A newly generated storage file uses YAML by default.
  3. Wait for startup, then run this in that server's console:
ccxstorage status

Look for backend=YAML. On standalone, the result should include gate=OPEN and transition=none. On Velocity, each group should be OPEN and transitions=none. Here, OPEN means storage operations are available; it does not control whether players can connect.

For Velocity, compare the listed scopes with the groups in velocity-config.properties. Do not replace custom groups with the default just to match an example.

Stop standalone Paper or Velocity again before editing the generated storage file in step 3. On a network, all JARs must be 2026.3.0 before players return; protocol 29 requires a coordinated update.

If startup reports missing or malformed data, or existing players' data appears unexpectedly empty, stop here and investigate using your backup. Do not select MYSQL to work around a YAML problem.

3. Set the database connection, keep YAML selected

Edit the storage file while the server is stopped.

Use plugins/CoreChatX/storage.yml for standalone Paper, or plugins/corechatx/velocity-storage.yml for Velocity. Edit the existing keys in that file. The examples below are partial: do not replace the whole file, add a second storage: section, or remove other generated settings.

SettingWhat to enter
backendKeep "YAML". You will change this only in step 5.
namespace / Paper scopeKeep your existing values. The defaults production and main identify a default installation; they are not database credentials.
mysql.host / portThe database hostname and port supplied by your host. db.example.net below is only an example. Use 127.0.0.1 only when MySQL is reachable at that address from the Java process.
mysql.database / usernameThe empty database and its dedicated user from step 1. They may have different names.
mysql.password / password-envChoose one of the password methods below. An empty password is not a request to create one.
ssl-modeKeep VERIFY_IDENTITY and use the hostname/certificate setup supplied by your host. Resolve TLS errors before migrating.
schema-auto-migrateNormally keep true: CoreChatX creates or updates its tables, including the persistent-channel field. This does not import your YAML player data.

Standalone Paper example

# Partial example: retain the other generated settings.
storage:
  backend: "YAML"
  namespace: "production"
  scope: "main"
  mysql:
    host: "db.example.net"
    port: 3306
    database: "corechatx"
    username: "corechatx"
    password: ""
    password-env: "CORECHATX_MYSQL_PASSWORD"
    ssl-mode: "VERIFY_IDENTITY"
    schema-auto-migrate: true

Velocity example

# Partial example: retain the other generated settings.
storage:
  backend: "YAML"
  namespace: "production"
  operation-timeout-ms: 15000
  mysql:
    host: "db.example.net"
    port: 3306
    database: "corechatx"
    username: "corechatx"
    password: ""
    password-env: "CORECHATX_MYSQL_PASSWORD"
    ssl-mode: "VERIFY_IDENTITY"
    schema-auto-migrate: true

Choose how to supply the database password

Hosting panel or service environment: set a variable named CORECHATX_MYSQL_PASSWORD to the actual database password in the environment used to launch Java. Keep password: "" and password-env: "CORECHATX_MYSQL_PASSWORD" as shown above. Restart the server process to load it.

If your host does not expose environment variables: edit these two keys inside the existing storage.mysql section instead. Replace the example text with your password and keep this file and its backups private.

    password: 'REPLACE_WITH_YOUR_DATABASE_PASSWORD'
    password-env: ""

Keep the indentation. With YAML single quotes, a single quote inside the password is written twice. Do not paste the example password literally. A nonblank environment value overrides password when password-env names that variable.

Start standalone Paper or Velocity again, still with YAML selected. Keep players blocked and network Paper servers stopped. Use a full stop/start; /corechatx reload does not apply storage connection or identity changes. Continue with 4A for standalone or 4B for Velocity.

Custom groups, TLS, or database schema managed by an administrator

Velocity derives its scopes from network-channel in velocity-config.properties. It has no Paper-style storage.scope setting. Keep every group's name and each Paper server's assignment unchanged.

VERIFY_IDENTITY needs a trusted certificate matching the configured database hostname. Configure trust in the Java runtime that starts Paper or Velocity. Do not assume that a working browser or database-panel login also configures Java's trust.

With schema-auto-migrate: false, have your database administrator arrange the required CoreChatX schema first; missing migrations are rejected. Legacy storage.sql.* keys do not enable MySQL.

Full defaults: Paper storage and Velocity storage.

4A. Standalone Paper only

Copy the YAML data into MySQL from the Paper console.

Server state: Paper running on 2026.3.0, backend YAML, player access blocked. Use the server console in your panel or terminal, not Minecraft chat. Console commands here have no leading slash. Run one command at a time and wait for its final response.

4A.1 — Check the source and database

ccxstorage check files

Expect Paper YAML valid, followed by sha256 and counts. These describe the existing files. Stop if the data is unexpectedly empty or an error is reported.

ccxstorage check mysql

Expect MySQL valid with a fingerprint and record counts. The target's counts can differ from YAML because it has not received the player data yet. With automatic schema migration enabled, this check can create the required tables. It does not copy your players into them.

4A.2 — Make and verify the additional data backup

ccxstorage backup files

The result includes backup=, sha256=, and archive=. Keep the archive. Copy only the value after backup= into the next command, without angle brackets or the backup= label:

ccxstorage backup verify <backup-id>

A successful verification returns that backup's ID, fingerprint, and archive path again. Use the ID or archive filename, not its full filesystem path. If needed, ccxstorage backup list lists the available filenames.

4A.3 — Create a migration plan

ccxstorage migrate files-to-mysql plan

The plan checks the source and destination and records the proposed operation. It does not import player data yet. Copy the actual values after run= and confirmation-token=. Execute within 10 minutes, without changing the source data or configuration.

Example: turn the plan values into an execute command

These are invented values to show the substitution, not a command to run unchanged. If the plan gave you:

run=11111111-1111-4111-8111-111111111111
confirmation-token=EXAMPLE_TOKEN

You would put the run ID first, a space, then the token:

ccxstorage migrate files-to-mysql execute 11111111-1111-4111-8111-111111111111 EXAMPLE_TOKEN

Use your own plan's values. Do not include labels, commas, angle brackets, or quotes.

4A.4 — Execute your plan

ccxstorage migrate files-to-mysql execute <run-uuid> <confirmation-token>

CoreChatX pauses data changes, saves pending YAML writes, makes a verified backup, checks that the source still matches the plan and the target is empty, then copies and verifies the data. Wait for the final result. Keep the YAML files and all generated recovery files.

Success tells you: YAML remains frozen. Change storage.backend to MYSQL and restart. Frozen means data changes are paused until activation; it is expected here.

4A.5 — Verify the copy before switching

ccxstorage migrate files-to-mysql status

Find your run ID. Its state should be VERIFIED_PENDING_CUTOVER: copied and verified, waiting for you to activate MySQL.

ccxstorage check parity <run-uuid>

Use the same run ID. Expect Parity verified for migration. Now go to step 5; skip the Velocity instructions. If any command fails, keep access blocked and use recovery instead of changing the backend.

4B. Velocity networks only

Copy every group's data from the Velocity console.

Server state: Velocity running on 2026.3.0 with YAML selected, Paper servers stopped, player access blocked. Use the Velocity console, not a Paper console or Minecraft chat. Run each command separately without a leading slash and wait for its final result.

--all-scopes means all configured CoreChatX groups. It is required even for one group: Velocity has one storage backend setting, so you cannot activate MySQL for only part of the same proxy.

4B.1 — Check every group and the database

ccxstorage status

Confirm backend=YAML, the expected scopes, every group marked OPEN, and transitions=none. Group names come from network-channel in velocity-config.properties, not the Paper server names.

ccxstorage check files --all-scopes

Expect a fingerprint and counts for each group. Stop if a group's existing data is unexpectedly missing or invalid.

ccxstorage check mysql --all-scopes

Expect a database result for every group and no connection/schema errors. The target has not received your YAML player data yet, so its counts need not match. This check can create tables with schema-auto-migrate: true; it does not import players.

4B.2 — Back up and verify every group

ccxstorage backup files --all-scopes

Save every returned archive. Each line contains a group's backup= ID. Run this command once for each ID, replacing the placeholder with only the ID value:

ccxstorage backup verify <backup-id>

A successful check returns the backup ID, fingerprint, and archive location. ccxstorage backup list lists the filenames if you need them. Supply the ID or filename, not a full path.

4B.3 — Plan all groups

ccxstorage migrate files-to-mysql plan --all-scopes

The console prints one plan per group. Keep each line's scope, run, and confirmation-token together. Copy scope names exactly as printed. Tokens expire after 10 minutes; do not change data or configuration between plan and execute.

4B.4 — Assemble one execute command

For each group, join its three values with equals signs: scope=run=token. Put every group on the same command line, separated by spaces. Do not include the labels scope=, run=, or confirmation-token= from the output.

If your only scope is corechatx:main, use:

ccxstorage migrate files-to-mysql execute --all-scopes corechatx:main=<run-uuid>=<confirmation-token>
Example with two groups

Suppose the plan returned these invented values:

scoperunconfirmation-token
corechatx:survival11111111-1111-4111-8111-111111111111EXAMPLE_SURVIVAL
corechatx:creative22222222-2222-4222-8222-222222222222EXAMPLE_CREATIVE

The assembled command would be one line:

ccxstorage migrate files-to-mysql execute --all-scopes corechatx:survival=11111111-1111-4111-8111-111111111111=EXAMPLE_SURVIVAL corechatx:creative=22222222-2222-4222-8222-222222222222=EXAMPLE_CREATIVE

Replace all example values with your actual plans. If three Paper servers all share one group, there is only one group entry; if your proxy lists more groups, include every one exactly once.

Run only the command matching your own group list. Wait for All Velocity scopes verified and the instruction to change storage.backend to MYSQL and restart. All groups remain paused until activation. An error affecting one group means you must resolve the transition before switching the whole proxy.

4B.5 — Verify before switching

ccxstorage migrate files-to-mysql status --all-scopes

Find each new run; every one should be VERIFIED_PENDING_CUTOVER, meaning copied and waiting for activation.

ccxstorage check parity --all-scopes

Expect Parity verified for all Velocity migration scopes. Continue with step 5. On failure, keep all player access blocked and follow recovery.

5. Activate MySQL

Now change one setting and restart.

Start this step only after step 4 succeeds and the console explicitly tells you to change the backend and restart. MySQL already contains the imported data; this step makes it the storage used for new reads and writes.

  1. Stop standalone Paper or Velocity normally. Keep player access blocked and network Paper servers stopped.
  2. Open the same storage file you edited in step 3: Paper's plugins/CoreChatX/storage.yml or Velocity's plugins/corechatx/velocity-storage.yml.
  3. Under storage:, change only backend: "YAML" to backend: "MYSQL". Leave database, password, namespace, scope, and network groups unchanged. Keep all source files and journals.
  4. Start that server again. Leave MySQL reachable and wait for CoreChatX startup to finish.
ccxstorage status

Confirm backend=MYSQL. On Paper, expect gate=OPEN and transition=none. On Velocity, expect all groups OPEN and transitions=none. This means the storage change has finished and data operations are available again.

Velocity only: now start the updated Paper servers in their existing PROXY mode and groups. Do not change their local storage backend to MYSQL. Admit only the players needed for step 6.

If MySQL startup fails, CoreChatX keeps storage-dependent features unavailable; it does not silently use YAML. Correct the reported connection, schema, ownership, or recovery problem. Changing the setting back to YAML by itself is not a rollback.

6. Check the result and reopen

Confirm the saved data and a new change both survive.

Open the commands for your installation. Run each command separately in the same Paper or Velocity console you used for migration.

Standalone Paper checks after activation

First, confirm that database access succeeds:

ccxstorage check mysql

Find your migration run and confirm its state is ACTIVE:

ccxstorage migrate files-to-mysql status

Make a backup of the current database data:

ccxstorage backup mysql

Use the returned backup ID to verify it:

ccxstorage backup verify <backup-id>
Velocity checks after activation

Confirm that database access succeeds for every group:

ccxstorage check mysql --all-scopes

Find every new migration run and confirm each is ACTIVE:

ccxstorage migrate files-to-mysql status --all-scopes

Make a current database backup for every group:

ccxstorage backup mysql --all-scopes

Run this once for each returned backup ID:

ccxstorage backup verify <backup-id>
  1. Connect your checking players and compare the values recorded in step 1: nickname, settings, selected/hidden channels, ignores, mutes, Discord links, and global chat state. On Velocity, check each group.
  2. Change one harmless preference in /ccxsettings, wait for its success response, then reconnect. Restart standalone Paper or Velocity once more and confirm the saved change remains.
  3. Check public chat, private messages, permissions, moderation, and whichever integrations you use. On Velocity, also send messages across Paper servers in the same group and check separation between different groups.
  4. When the checks pass, restore normal player access and integration traffic. Retain the original full backup and the new verified archives.

After migration: new runtime data goes into MySQL. The old YAML data files are not a continuously updated mirror, so do not compare them to live MySQL or edit them expecting live changes. Your configuration files still belong in the plugin folder.

check parity is used during an unfinished migration or rollback, before activation. It is not the daily health check for an already active MySQL setup. Keep your normal database backup policy too; backup mysql contains CoreChatX's logical data, not the whole database server.

For more feature checks, see setup verification. Use an isolated copy for interruption, database-unavailability, or rollback rehearsals instead of interrupting a server open to players.

Optional: return to YAML without losing newer MySQL data.

You do not run this after a successful migration unless you want to return to YAML. It keeps CoreChatX 2026.3.0 installed. It does not downgrade the plugin to 2026.2.6.

Once players have used MySQL, the old YAML backup is out of date. The rollback commands export the current MySQL data into new YAML files before switching back. Simply selecting YAML or restoring the original folder could lose those newer changes.

  1. Block player access and data changes again. Make current backups. On Velocity, stop Paper servers; keep Velocity running. Standalone Paper stays running. Keep the current backend: "MYSQL" and a working database connection.
  2. Use the plan command below for your platform. It prints new rollback run IDs and tokens. Do not reuse the earlier migration values.
  3. Substitute those values into execute, run it once, and wait for successful staging/verification. Then run status and parity, one command at a time.
Standalone Paper rollback commands 
ccxstorage rollback mysql-to-files plan

Use the returned rollback ID and token:

ccxstorage rollback mysql-to-files execute <rollback-run-uuid> <rollback-token>
ccxstorage rollback mysql-to-files status
ccxstorage check parity <rollback-run-uuid>
Velocity rollback commands 
ccxstorage rollback mysql-to-files plan --all-scopes

Use the same group=run=token assembly as step 4B, with the new rollback values for every group. This template applies only to a single corechatx:main group:

ccxstorage rollback mysql-to-files execute --all-scopes corechatx:main=<rollback-run-uuid>=<rollback-token>
ccxstorage rollback mysql-to-files status --all-scopes
ccxstorage check parity --all-scopes

Only when instructed to change the backend and restart:

  1. Stop standalone Paper or Velocity. In the same storage file, change only backend: "MYSQL" to backend: "YAML".
  2. Start it again with MySQL still reachable: startup must verify the rollback before activating the new files. Keep all journals and staging folders. Former files are retained under storage-rollbacks/<run>-originals.
  3. Run ccxstorage status. Expect YAML, storage operations OPEN, and no unfinished transition. Run ccxstorage check files on standalone or ccxstorage check files --all-scopes on Velocity.
  4. Start the network's Paper servers if applicable, repeat the player checks, and make a fresh files backup before reopening.

Do not delete MySQL or make it unreachable before rollback activation has finished. A downgrade to 2026.2.6 needs a separately planned full restoration and a decision about any newer data it would discard. Replacing a JAR does not downgrade a database schema.

If something fails, stop and read the current state.

Do not paste all recovery commands in sequence. First read ccxstorage status and the relevant migration or rollback status. Use resume to continue a supported unfinished operation, or abort to cancel it only when CoreChatX can verify that cancellation is safe. After MySQL is active, use the rollback procedure above instead of aborting the old migration.

If execute, restart, or resume fails, keep traffic blocked and preserve the whole plugin folder, backups, journals, staging files, and console output. Recovery-only startup keeps storage changes disabled, but its server socket may still accept connections without normal CoreChatX gameplay services. Keep joins blocked until recovery and the required restart have completed. Do not delete a journal, edit frozen YAML, truncate database tables, or change namespace/groups to bypass the error.

Observed problemNext action
Connection, authentication, TLS, or schema check failsCorrect the owning process's connection/environment or database setup. Restart to apply edited storage settings; rerun checks before planning.
Target is nonempty or has another active ownerVerify the intended database and storage identity. Keep the existing data; do not force-import or erase it. Resolve ownership or select a deliberately isolated migration target before creating a new plan.
Token expired, was lost, or the source changed after planningInspect the existing run. Use the direction-specific safe abort, then create a fresh plan after the source is stable. If execution already created a journal, follow recovery state; do not blindly execute a new run.
Process stopped during import or file promotionStart the same installation with its journals intact. Read status/history and use the matching resume command when the recorded state supports it. Run parity checks for the open transition; follow the returned restart instruction.
Abort cannot prove the database state is safeKeep storage frozen and restore database access so recovery can inspect the durable run. Do not reopen YAML manually. After a successful abort in recovery-only mode, restart as instructed to reconstruct normal services. A fresh plan uses new run IDs and tokens; a verified abort does not require deleting the old journal.

Run IDs are valid only for the configured namespace and storage scope. Aborting a planned or failed files-to-MySQL run changes its history without deleting runtime data. An imported run can remove its staged rows only with unchanged canonical contents, no active runtime lease and no other incomplete transition. Changed data or an ambiguous RUNNING state causes abort to refuse deletion; preserve the files and database while investigating.

If Paper reports malformed or unreadable persistent YAML, repair the identified file or restore a verified backup. It will not replace the file with empty defaults. A failed player/global reload also prevents later flushes until a successful reload; deleting live data is not a recovery step.

Use these corrected 2026.3.0 builds throughout recovery. Verified aborts are recorded as ABORTED; earlier builds cannot read that new local state. Do not downgrade JARs or edit the journal to bypass recovery checks. If a process loses its database lease to another owner, restore database access and restart the intended owner after resolving the conflict; the retired process cannot safely resume writes.
