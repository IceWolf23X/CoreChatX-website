Before anything else, back up every file in the CoreChatX plugin folder. Stop the affected servers gracefully, then copy the entire folder, including every file and subfolder, to a separate backup location before replacing JARs, editing configuration, or running migration commands.

On Paper, back up plugins/CoreChatX/. On a Velocity network, also back up plugins/corechatx/ on the proxy, including all of data/groups/, and the CoreChatX folder on every Paper backend. Include configuration, player data, credentials, journals, and existing backups. Verify that the copy is complete before continuing.

1. Prepare and back up

Keep a complete, stopped-server recovery copy.

  1. Schedule a maintenance window and block normal joins. Disconnect players and prevent integrations, scheduled commands, and operators from changing CoreChatX data during the migration.
  2. Stop standalone Paper, or stop Velocity and all affected Paper backends gracefully. Preserve the 2026.2.6 JARs and copy the complete plugin folders to a separate backup location.
  3. For standalone, preserve the runtime files such as playerdata.yml, state.yml, channeldata.yml, ignoredata.yml, mutedata.yml, and discordlinks.yml. For Velocity, preserve all of data/groups/; do not rename its encoded directories or copy only one group.
  4. Record representative existing player values: nickname, locale, active and hidden channels, notification preferences, ignores, mutes, Discord links, and global chat state. On a network, record players in each group.
  5. Have a MySQL database and a dedicated account ready. Use an empty dedicated database for the first migration; CoreChatX checks that each target scope has no existing runtime data or active owner. The account needs runtime read/write access and the schema creation/alteration permissions used by automatic schema migration.
  6. Check database reachability from the owning server, verified TLS, free space for backups and staging, and access to the server console. Keep the staging database separate from production; never start two copies against the same storage identity.

The built-in storage backup created later is an additional verified archive. It excludes credentials and storage configuration, so it does not replace this full plugin-folder backup. Keep any existing journals and rollback directories with their installation.

2. Upgrade while using YAML

Load your existing data with 2026.3.0.

  1. Replace the plugin JAR with the 2026.3.0 artifact for that platform. Remove the old JAR from the live plugins/ directory, retaining the backup. On a network, update Velocity and every Paper backend together: 2026.3.0 uses protocol 29, so do not mix builds.
  2. Keep your existing configuration and runtime files. Start the storage owner with joins still blocked and YAML selected. Let 2026.3.0 generate or supplement its configuration, then inspect startup logs and run ccxstorage status from that console.
  3. Confirm the selected backend is YAML and the deployment identity is the one you intend to migrate. For Velocity, confirm every existing network-channel group in velocity-config.properties is still present.
  4. Stop the owner gracefully again before editing the generated storage configuration. Keep proxy Paper backends stopped until the proxy has completed its migration.

If the source files are missing, malformed, or unexpectedly empty, stop here and resolve the source problem from your backup. Do not initialize an empty MySQL installation in place of an intended migration.

3. Configure the connection

Provide database settings while leaving YAML authoritative.

Merge the relevant example into the generated file, retaining its other timeout, pool, and executor settings. Replace the example database host, database name, and username with your own. Keep your existing namespace and scope values if they differ from the defaults shown here.

Standalone: storage.yml

# Partial example: retain the other generated settings.
storage:
  backend: "YAML"
  namespace: "production"
  scope: "main"
  mysql:
    host: "db.example.net"
    port: 3306
    database: "corechatx"
    username: "corechatx"
    password: ""
    password-env: "CORECHATX_MYSQL_PASSWORD"
    ssl-mode: "VERIFY_IDENTITY"
    schema-auto-migrate: true

Velocity: velocity-storage.yml

# Partial example: retain the other generated settings.
storage:
  backend: "YAML"
  namespace: "production"
  operation-timeout-ms: 15000
  mysql:
    host: "db.example.net"
    port: 3306
    database: "corechatx"
    username: "corechatx"
    password: ""
    password-env: "CORECHATX_MYSQL_PASSWORD"
    ssl-mode: "VERIFY_IDENTITY"
    schema-auto-migrate: true
  • Set CORECHATX_MYSQL_PASSWORD in the environment inherited by the Java server process or its service. Setting it in an unrelated shell will not update an already running server. A nonblank environment value overrides the inline password.
  • VERIFY_IDENTITY requires a trusted database certificate matching the configured hostname. Configure trust for the Java runtime that launches the owner; resolve certificate errors before continuing.
  • schema-auto-migrate: true lets CoreChatX apply its checksummed schema migrations, including V003 for the persistent-channel preference. If your database policy requires false, arrange the required CoreChatX schema with your database administrator first; an incomplete schema is rejected.
  • Velocity derives scopes from its configured network-channel groups. There is no standalone-style storage.scope setting on Velocity. Preserve the group list and Paper group assignments.

Start the owner again with backend: "YAML". Storage connection settings and identity are bound at startup; /corechatx reload is not sufficient. Keep normal traffic blocked and continue with Paper or Velocity.

Full defaults: Paper storage and Velocity storage.

4A. Standalone Paper

Validate, plan, and import the standalone data.

Use the Paper server console. Command examples on this page omit the leading slash for console entry. Replace angle-bracket placeholders with returned values; do not paste the brackets. Run commands one at a time and wait for each final result.

Check the source, connection, and backup

ccxstorage status
ccxstorage check files
ccxstorage check mysql
ccxstorage backup files
ccxstorage backup list
ccxstorage backup verify <backup-id-or-file>

Expect the intended YAML identity, an open maintenance gate, no unfinished transition, a valid YAML snapshot, a successful MySQL check, and a verified backup. Keep the reported hashes, counts, and backup location. Resolve failures before planning.

Create the plan

ccxstorage migrate files-to-mysql plan

Copy run and confirmation-token from the result and review its scope, source hash, and counts. The token expires after 10 minutes. Planning records a durable run but does not import player data. Keep the source unchanged between plan and execute.

Execute and verify before changing backend

ccxstorage migrate files-to-mysql execute <run-uuid> <confirmation-token>
ccxstorage migrate files-to-mysql status
ccxstorage check parity <run-uuid>

Execution drains pending mutations, flushes YAML, checks that the source still matches the plan, creates a verified backup, checks the target is empty, imports the canonical snapshot, and verifies parity. YAML then remains frozen under a durable journal.

Continue only after the migration reports successful verification and instructs you to change storage.backend to MYSQL and restart. The database run is VERIFIED_PENDING_CUTOVER; migration is not yet active. Proceed to activation. On any error, use recovery.

4B. Velocity network

Migrate all configured groups in one transition.

Use the Velocity console, with normal joins blocked and Paper backends stopped. Commands below omit the leading slash. Run them one at a time, wait for each final result, and replace angle-bracket placeholders without including the brackets. Even a one-group proxy uses --all-scopes for backend transitions because Velocity has one global backend selection.

Check and back up every group

ccxstorage status
ccxstorage check files --all-scopes
ccxstorage check mysql --all-scopes
ccxstorage backup files --all-scopes
ccxstorage backup list
ccxstorage backup verify <backup-id-or-file>

Confirm the expected group list, valid source snapshots, successful MySQL checks, and no unfinished transition. Repeat backup verify for each returned archive. Read-only checks and backups can also select --scope <group>; the migration itself cannot switch only one group.

Plan every group

ccxstorage migrate files-to-mysql plan --all-scopes

The result contains a scope, run UUID, source hash, token, and expiry for each group. Copy the exact scope strings, such as corechatx:main, rather than Paper server names or encoded folder names. All tokens expire after 10 minutes.

Supply every group confirmation in one command

For a proxy with only corechatx:main:

ccxstorage migrate files-to-mysql execute --all-scopes corechatx:main=<run-uuid>=<confirmation-token>

For an example proxy with exactly corechatx:survival and corechatx:creative, use one line containing both confirmations:

ccxstorage migrate files-to-mysql execute --all-scopes corechatx:survival=<survival-run-uuid>=<survival-token> corechatx:creative=<creative-run-uuid>=<creative-token>

Use only the example matching your actual group list, substitute all values, and include every configured group exactly once. Do not run both examples or change the group configuration to fit an example.

ccxstorage migrate files-to-mysql status --all-scopes
ccxstorage check parity --all-scopes

CoreChatX freezes all groups and publishes their journals before import. Continue only when every scope is verified and the console instructs you to change the backend and restart. A partial import is a recovery case, not permission to activate the completed groups. Continue with activation.

5. Activate MySQL

Follow the verified migration's restart instruction.

  1. After successful execution and parity checks, stop the storage owner gracefully. Preserve the source YAML, generated backups, and transition journals.
  2. In standalone storage.yml or proxy velocity-storage.yml, change only storage.backend from YAML to MYSQL. Retain the exact database, namespace, and scope/group identity used by the plan.
  3. Start the owner with the database reachable and normal joins still blocked. Startup verifies the pending run, acquires the authoritative lease, loads runtime state, activates MySQL, and closes the local transition journal.
  4. Inspect startup logs and ccxstorage status. Expect the intended MYSQL identity, an open gate, and no open transition. Confirm the migration run is ACTIVE in its status/history output.
  5. For Velocity, start the updated Paper backends after the proxy is ready. Keep them in PROXY mode with their original group assignments, then admit only your test players.

If MySQL startup fails, CoreChatX keeps storage-dependent services unavailable instead of falling back to YAML. Fix the reported database, schema, lease, or recovery problem. Editing the backend back to YAML is not a rollback.

6. Verify before reopening

Check stored data and player-visible behavior.

Standalone console

ccxstorage status
ccxstorage check mysql
ccxstorage migrate files-to-mysql status
ccxstorage history
ccxstorage backup mysql
ccxstorage backup verify <backup-id-or-file>

Velocity console

ccxstorage status
ccxstorage check mysql --all-scopes
ccxstorage migrate files-to-mysql status --all-scopes
ccxstorage history --all-scopes
ccxstorage backup mysql --all-scopes
ccxstorage backup verify <backup-id-or-file>

Verify every proxy backup archive separately. backup mysql produces a logical CoreChatX snapshot; also retain your normal database backup policy. check parity is for an open migration/rollback transition, not a routine comparison against stale YAML after MySQL becomes active.

  • Compare the representative player values recorded before migration. Confirm nickname, locale, ignores, mutes, hidden channels, Discord links, and global settings survived.
  • Change a harmless preference through /ccxsettings, wait for its success response, reconnect, and restart the owner once more. Confirm the committed value survives. Existing players default to Persistent channels; test both compass choices.
  • Test public/channel chat, private messages, permissions, moderation, and the enabled Discord or Telegram features with authenticated players.
  • On Velocity, test cross-server traffic and backend transfers inside each group, plus isolation between different groups.
  • In staging, rehearse rollback, restart interruptions, and database unavailability. Measure performance on representative data and load before production acceptance.

Reopen access only after the checks required for your installation pass. Keep the original recovery copy and verified archives. Complete the runtime acceptance checks for your installation before reopening.

Return to YAML using the latest MySQL data.

This is a storage rollback within 2026.3.0. It is not a downgrade to 2026.2.6. Block joins and data changes again, keep the MySQL connection available, and use the storage owner's console.

Standalone Paper

Plan first, then use the new rollback run UUID and token from that result:

ccxstorage rollback mysql-to-files plan
ccxstorage rollback mysql-to-files execute <rollback-run-uuid> <rollback-token>
ccxstorage rollback mysql-to-files status
ccxstorage check parity <rollback-run-uuid>

Velocity

Plan every group, then supply one group=run=token entry per configured group on the same execute line. The example below is for a proxy whose only group is corechatx:main:

ccxstorage rollback mysql-to-files plan --all-scopes
ccxstorage rollback mysql-to-files execute --all-scopes corechatx:main=<rollback-run-uuid>=<rollback-token>
ccxstorage rollback mysql-to-files status --all-scopes
ccxstorage check parity --all-scopes

For multiple groups, use the same all-group confirmation format as the forward migration, with the new rollback UUIDs and tokens. Do not reuse forward-migration confirmations.

  1. Wait for successful staging/verification and the explicit instruction to select YAML. MySQL remains frozen during this transition.
  2. Stop the owner, change only storage.backend to YAML, and restart. Keep the database reachable: startup still verifies the durable rollback evidence.
  3. CoreChatX promotes the staged files, retains former files under storage-rollbacks/<run>-originals, verifies parity, and activates YAML. Confirm status reports an open gate with no open transition; run check files on Paper or check files --all-scopes on Velocity.
  4. Repeat player checks and make a fresh verified files backup before reopening.

Do not restore the pre-migration YAML archive over an installation that has accepted newer MySQL writes: those writes would be lost. A downgrade to 2026.2.6 needs a separately planned and tested full restoration with an explicit data-loss boundary. Replacing the JAR is not a database downgrade; older MySQL-capable builds also reject schema version 3.

Recover from an interruption without discarding evidence.

If execute, restart, or resume fails, keep traffic blocked and preserve the whole plugin folder, backups, journals, staging files, and console output. Recovery-only startup keeps the mutation gate closed, but its server socket may still accept connections without normal CoreChatX gameplay services. Keep joins blocked until recovery and the required restart have completed. Do not delete a journal, edit frozen YAML, truncate database tables, or change namespace/groups to bypass the error.

Observed problemNext action
Connection, authentication, TLS, or schema check failsCorrect the owning process's connection/environment or database setup. Restart to apply edited storage settings; rerun checks before planning.
Target is nonempty or has another active ownerVerify the intended database and storage identity. Keep the existing data; do not force-import or erase it. Resolve ownership or select a deliberately isolated migration target before creating a new plan.
Token expired, was lost, or the source changed after planningInspect the existing run. Use the direction-specific safe abort, then create a fresh plan after the source is stable. If execution already created a journal, follow recovery state; do not blindly execute a new run.
Process stopped during import or file promotionStart the same installation with its journals intact. Read status/history and use the matching resume command when the recorded state supports it. Run parity checks for the open transition; follow the returned restart instruction.
Abort cannot prove the database state is safeKeep storage frozen and restore database access so recovery can inspect the durable run. Do not reopen YAML manually. After a successful abort in recovery-only mode, restart as instructed to reconstruct normal services. A fresh plan uses new run IDs and tokens; a verified abort does not require deleting the old journal.

Run IDs are valid only for the configured namespace and storage scope. Aborting a planned or failed files-to-MySQL run changes its history without deleting runtime data. An imported run can remove its staged rows only with unchanged canonical contents, no active runtime lease and no other incomplete transition. Changed data or an ambiguous RUNNING state causes abort to refuse deletion; preserve the files and database while investigating.

If Paper reports malformed or unreadable persistent YAML, repair the identified file or restore a verified backup. It will not replace the file with empty defaults. A failed player/global reload also prevents later flushes until a successful reload; deleting live data is not a recovery step.

Use these corrected 2026.3.0 builds throughout recovery. Verified aborts are recorded as ABORTED; earlier builds cannot read that new local state. Do not downgrade JARs or edit the journal to force acceptance. If a process loses its database lease to another owner, restore database access and restart the intended owner after resolving the conflict; the retired process cannot safely resume writes.

ccxstorage migrate files-to-mysql resume <run-uuid> [confirmation-token]
ccxstorage migrate files-to-mysql abort <run-uuid>
ccxstorage rollback mysql-to-files status
ccxstorage rollback mysql-to-files resume <run-uuid> [confirmation-token]
ccxstorage rollback mysql-to-files abort <run-uuid>

Velocity recovery commands

ccxstorage status
ccxstorage history --all-scopes
ccxstorage migrate files-to-mysql status --all-scopes
ccxstorage migrate files-to-mysql resume --all-scopes [<group>=<token> ...]
ccxstorage migrate files-to-mysql abort --all-scopes
ccxstorage rollback mysql-to-files status --all-scopes
ccxstorage rollback mysql-to-files resume --all-scopes [<group>=<token> ...]
ccxstorage rollback mysql-to-files abort --all-scopes

These are alternatives, not a script to run from top to bottom. Choose the operation matching the open transition. Square brackets denote optional confirmation arguments required by some pre-import states; omit the brackets when entering a command. Resume does not bypass expired tokens or invalid state. Once MySQL is active, use a new rollback plan rather than trying to abort the completed forward migration.
