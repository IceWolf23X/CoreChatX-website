Optional Velocity network feature

Synchronize full advancement progress across one group.

CoreChatX 2026.3.1 can keep advancement criteria, partial progress, completion dates, and revocations consistent across Paper backends in the same Velocity group. It is disabled by default.

1. Prepare safely

Choose one synchronization owner and keep recovery data.

Before changing anything: stop the affected servers and back up the complete CoreChatX plugin folders, complete Minecraft worlds, and the CoreChatX database when MySQL is used. Keep every backend's existing advancement files until each player has visited the backends that contain progress to import.

Disable advancement synchronization in other plugins before enabling CoreChatX. Two synchronizers can overwrite each other or replay rewards and announcements.

Install matching 2026.3.1 Paper and Velocity JARs on all participating servers. This feature is for PROXY mode; it does not run on standalone Paper.

2. Pin the group

Give every participating Velocity backend an explicit group pin.

In Velocity plugins/corechatx/velocity-config.properties, list the group and pin each backend name from Velocity's server list. Each Paper server must use the same group with a matching deployment.server-id.

network-channel=corechatx:main
backend-groups.alpha-1=corechatx:main
backend-groups.alpha-2=corechatx:main

On each participating Paper backend, use deployment.mode: "PROXY", deployment.network-features-allowed: true, the same deployment.network-channel, and a deployment.server-id that matches its Velocity backend name.

3. Create credentials

Use a different secret for every backend.

Generate at least 32 cryptographically random bytes for each backend, encoded as Base64 or a URL-safe equivalent. Tokens must be 43–256 characters and must not be reused. Prefer environment variables so secrets are not embedded in shared configuration or source control.

Each Paper process needs only its own value. The matching Velocity backend entry needs the same value. Never publish the values.

4. Enable Velocity

Configure the authenticated authority endpoint.

Start Velocity once to create plugins/corechatx/velocity-advancements.properties, then stop it and edit the file:

enabled=true
port=8767
backend.alpha-1.group=corechatx:main
backend.alpha-1.token=${CORECHATX_ADVANCEMENT_ALPHA_1_TOKEN}
backend.alpha-2.group=corechatx:main
backend.alpha-2.token=${CORECHATX_ADVANCEMENT_ALPHA_2_TOKEN}

The listener binds only to 127.0.0.1. It stores advancement authority through the normal Velocity YAML or MySQL storage configuration; Paper does not receive direct database access.

For Paper on another machine or isolated network, use an HTTPS reverse proxy or encrypted tunnel to the proxy loopback listener. Do not use remote plaintext HTTP. The route must preserve /corechatx/advancements, forward the Authorization and X-CoreChatX-Backend headers and POST bodies, allow at least 4 MiB plus 66 bytes, allow roughly 22 seconds for a request, and retain certificate verification.

5. Enable Paper

Configure every participating backend.

In each participating backend's plugins/CoreChatX/config.yml, set its endpoint and its own matching secret:

advancement-sync:
  enabled: true
  endpoint: "http://127.0.0.1:8767/corechatx/advancements"
  token: "${CORECHATX_ADVANCEMENT_TOKEN}"

Use literal 127.0.0.1 or ::1 only when the endpoint is local to that Paper process's network namespace. Otherwise use your HTTPS route. This setup is restart-scoped: /corechatx reload does not enable the service or replace endpoint credentials.

6. Start and verify

Test progress, restoration, and revocations before regular play.

  1. Start Velocity first and confirm that storage is ready and the advancement endpoint starts on the selected port.
  2. Start the participating Paper backends and inspect each console for endpoint or credential errors.
  3. With a test player, complete one advancement or part of a multi-criterion advancement on one backend.
  4. Move that player to another backend in the same group and confirm the progress arrives without replaying historical chat, toasts, XP, loot, or functions.
  5. Visit every backend that holds existing progress for the test player and confirm the union is preserved.
  6. Test an explicit revocation, revisit an older backend, and confirm the revoked criterion does not return.
  7. Disconnect the last player, reconnect through another backend, then repeat after a graceful Paper restart. Take and verify a fresh CoreChatX storage backup.

New completions use normal Minecraft behavior locally and can announce live to other enabled backends in the group. This feature does not synchronize inventories, XP balances, statistics, or the recipe book.

Operations and limits

Keep the authority healthy and understand the upgrade boundary.

Progress imports progressively when a player visits a backend; CoreChatX does not scan every world file offline. Explicit revocations are retained when older positive progress is later imported. Unknown advancement IDs remain stored but can only be applied where that advancement exists, so use matching Minecraft versions and datapacks across participating servers.

A failed or timed-out authority exchange blocks unsafe progress or transfer and disconnects the affected player with an availability message. Inspect the Paper and Velocity consoles; do not delete progress to work around an outage.

MySQL installs receive schema migration V004 and ccx_player_advancements, even when advancement synchronization remains disabled. Normal schema auto-migration applies it at startup. If schema-auto-migrate=false, arrange the upgrade before boot; older builds reject schema version 4, so replacing only the JAR is not a database downgrade.

Canonical backups that contain advancement records use format 3 and retain them through Velocity YAML-to-MySQL migration and rollback. Format 1 and 2 backups remain readable; snapshots without advancement records keep their existing format. For an orderly full-network shutdown, stop Paper backends first so final saves can drain, then stop Velocity.
