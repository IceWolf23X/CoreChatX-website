Overview

This page is generated from the current CoreChatX bundled defaults in the plugin source tree. The YAML blocks below are complete file contents, including comments, so an admin can inspect the exact default shape before installing or resetting a file.

Paper config files live under plugins/CoreChatX/. Velocity config lives under plugins/corechatx/. The Paper jar belongs on Paper backends only, and the Velocity jar belongs on Velocity only.

  • Current release: 2026.1.8
  • Installable jars: corechatx-paper-2026.1.8.jar and corechatx-velocity-2026.1.8.jar
  • Paper target: 1.21.11
  • Java target: 21
  • Default Paper network channel: corechatx:main

Before You Configure

Use this document as the operational reference for a real installation. It is intentionally more detailed than the feature list because it documents the files, runtime gates, restart requirements, proxy grouping, and safety limits that matter when the plugin is already installed on a server.

Minimum expectations:

  • Java 21 runtime.
  • Paper 1.21.11 for backend servers.
  • Velocity for multi-backend network installs.
  • The Paper CoreChatX jar installed only on Paper backends.
  • The Velocity CoreChatX jar installed only on Velocity.

Core terminology:

  • STANDALONE means one Paper server without cross-backend CoreChatX routing.
  • PROXY means a Paper backend connected to a Velocity network.
  • server-id is the unique CoreChatX identity of one Paper backend.
  • deployment.network-channel is the Paper backend group identity used by Velocity.
  • A Velocity network-channel list defines one or more isolated CoreChatX proxy groups.
  • Runtime data files are live player/plugin state, not decorative default config.

High-level runtime model:

  • Paper owns chat parsing, formatting, commands, moderation, player settings, chat items, bubbles, pings, nicknames, and bridge rendering.
  • Velocity relays network packets, group player directory data, completions, TAB entries, state sync, true network join/leave, and remote ChatItem snapshot requests.
  • External bridges are configured on Paper and can export only the channels that opt in.
  • Player-authored chat is sanitized and controlled before it becomes a rendered Adventure component.
  • Server-controlled templates can use MiniMessage and, where supported, PlaceholderAPI.

2026.1.8 Notes

This release rolls the 2026.1.7.1 hotfix line forward into a stable release focused on Discord account linking, safer group-local sync, and nickname-aware lookup.

  • Join/leave delivery mode: config.yml -> join-quit.mode chooses LOCAL backend announcements or NETWORK proxy-routed announcements.
  • Velocity proxy groups: velocity-config.properties -> network-channel now accepts a comma-separated list. Each configured channel is an isolated CoreChatX group.
  • Persistent nicknames: /nick stores a CoreChatX nickname, syncs it through same-group player state in proxy mode, and can be limited to color/style-only changes through nicknames.change-only-colors.
  • Nickname placeholders: {player_name} always means the real Minecraft username. {player_nickname} uses the custom nickname when present and includes nicknames.prefix.
  • Safe nickname formatting: nicknames accept legacy colors, legacy hex, safe MiniMessage colors, formats, hex, and gradients. Unsupported MiniMessage tags are stripped.
  • Real-name lookup: /realname <nickname> resolves a saved custom nickname back to the real Minecraft username, with proxy-group nickname suggestions when network directory sync is available.
  • Nickname-aware mentions: chat suggestions include real names and custom nicknames, and mention tokens can display the target's custom nickname.
  • Discord account linking: optional linking adds Minecraft-side /discord link, Discord slash /link code:<code>, unlink commands, discordlinks.yml, linked Minecraft identity rendering, mute checks, and channel permission checks for Discord inbound.
  • Discord link-to-play: discord.inbound.account-linking.require-linked-to-play can kick unlinked Minecraft players with a temporary Discord link code, but only when the Discord inbound bridge is running and the bot can expose the configured slash commands.
  • State safety fixes: settings updates preserve saved nicknames, local player-state updates reject stale remote sync, and Discord link sync ignores stale remote link/unlink packets inside the same proxy group.
  • Protocol compatibility: plugin-message protocol is 13; Paper and Velocity must run matching 2026.1.8 jars.

Reload vs Restart

Safe with /corechatx reload:

  • message wording, chat formats, pings, filters, ChatItems, keywords, chat bubbles, channel rules, privacy, moderation, storage, bridge formats, and locale files
  • join-quit.mode, join-quit.join-enabled, and join-quit.quit-enabled
  • nicknames.prefix and nicknames.change-only-colors
  • non-identity runtime toggles such as debug, hooks, logging, bridge gates, first-join, and reload summary behavior

Requires restart:

  • config.yml -> deployment.mode
  • config.yml -> deployment.server-id
  • config.yml -> deployment.network-channel
  • Velocity velocity-config.properties, including network-channel list changes

Transport settings are identity settings. If a change affects which backend or which proxy group a server belongs to, restart the affected backend or proxy instead of relying on reload.

Quick Install Patterns

Standalone Paper

Use the default backend config and keep deployment.mode: "STANDALONE". No Velocity module is required, proxy PM routing is inactive, and network player directory/TAB data is inactive.

deployment:
  mode: "STANDALONE"
  server-id: "paper-1"
  network-channel: "corechatx:main"
  bridges-allowed: true
  network-features-allowed: false

Single Velocity group

This is the legacy network shape. Every participating Paper backend uses the same deployment.network-channel, and Velocity has one matching network-channel value.

network-channel=corechatx:main

Multiple Velocity groups

Use a comma-separated Velocity list. Each Paper backend stays unchanged and chooses its group through its own deployment.network-channel.

network-channel=corechatx:survival,corechatx:minigames

Example: survival Paper servers use deployment.network-channel: "corechatx:survival", while minigame Paper servers use deployment.network-channel: "corechatx:minigames".

Velocity Proxy Groups

Paper still has one channel value: config.yml -> deployment.network-channel. Velocity can now configure one or more accepted channels with a comma-separated list in velocity-config.properties.

network-channel=corechatx:survival,corechatx:minigames

Each channel is a separate group. Backends using corechatx:survival route only with other survival backends. Backends using corechatx:minigames route only with minigames backends.

  • Network chat, PMs, player directory, TAB/completions, state sync, ChatItem snapshots, and join/leave routing stay inside the source group.
  • Private messages search only players known in the sender's group. A player on another group behaves like player-not-found.
  • A backend whose Paper channel is not configured on Velocity keeps local features, but proxy features for that backend are not routed.
  • Velocity learns backend membership through plugin messages and a registration handshake; servers without known membership do not receive network routing yet.
  • Server switches inside one group suppress artificial leave/join announcements. Switches between groups produce quit in the old group and join in the new group.

Nicknames

/nick changes the CoreChatX display name only. It does not change the real Minecraft username or UUID identity used for lookup, replies, ignores, privacy, routing, or state sync.

  • /nick <nickname> sets your nickname.
  • /nick off, /nick clear, or /nick reset clears it.
  • /nick <player> <nickname|off> changes another online player's nickname with staff permission.
  • /realname <nickname> resolves a saved custom nickname to the real Minecraft username.
  • corechatx.command.nick controls self-use.
  • corechatx.command.nick.others controls editing other players.
  • corechatx.nick.color and corechatx.nick.format grant all nickname colors/styles through child permissions.
  • Granular examples: corechatx.nick.color.red, corechatx.nick.color.gold, corechatx.nick.format.bold, corechatx.nick.format.italic.

When nicknames.change-only-colors: true, the visible text after formatting is stripped must match the real Minecraft username exactly. For example, &cIceWolf23X can be accepted for player IceWolf23X, while &cIceWolf is rejected.

Mentions and tab suggestions understand both real names and custom nicknames. In proxy mode, this includes players known through the same Velocity channel group, so nickname suggestions and /realname completions do not stop at the current backend.

Paper YAML Files

These are the complete bundled YAML resources from the Paper jar source. Existing installs receive missing bundled default keys automatically when valid config files are loaded; existing values are not overwritten.

config.yml

Main Paper runtime settings: deployment identity, proxy transport gates, hooks, logging, nickname mode, join/leave mode, and reload summary.

Purpose:

  • Controls the Paper backend deployment mode and backend identity.
  • Defines deployment.network-channel, which is the group identity used by Velocity routing.
  • Holds proxy feature gates, Discord/Telegram bridge gates, hook toggles, logging toggles, player-data save behavior, nickname behavior, first-join behavior, join/quit behavior, and reload summary behavior.

Operational notes:

  • deployment.mode, deployment.server-id, and deployment.network-channel are boot identity values and require restart.
  • In PROXY mode, deployment.network-features-allowed: true is still required before cross-server chat, PM routing, player directory sync, state sync, ChatItem snapshot routing, or network join/leave can run.
  • join-quit.mode: LOCAL announces only on the current Paper backend. NETWORK routes true proxy join/leave through Velocity when proxy routing is available.
  • nicknames.change-only-colors: true means /nick may only recolor/restyle the real Minecraft username; shortened or changed visible text is rejected.
  • deployment.pending-pm-timeout-seconds protects remote PM requests from waiting forever if the proxy route cannot answer.

Current bundled default:

messages.yml

Player-facing messages and command feedback. Nickname, PM, moderation, join/quit, and ChatItem wording live here.

Purpose:

  • Stores the visible text for command feedback, errors, settings, privacy, moderation, cooldowns, pings, private messages, join/quit, ChatItems, bubbles, channels, bridges, and nicknames.
  • Controls the MiniMessage templates used for PM display, social-spy display, network join/leave output, nickname command responses, and Discord link feedback.
  • Keeps wording centralized so admins can translate or restyle feedback without touching code.

Important notes:

  • Strings use MiniMessage in server-controlled templates. Keep tags valid when editing.
  • Placeholder availability is message-specific. The header comments list common placeholders, but not every placeholder applies to every message.

  • The nickname messages are used by /nick and /realname, including permission stripping, duplicate rejection, color-only rejection, and staff edits for other online players.
  • The Discord messages are used by Minecraft-side account-link commands and the optional link-required kick reason.

chat.yml

Public chat formatting, PlaceholderAPI behavior, cooldown defaults, mention defaults, and formatting permission behavior.

Purpose:

  • Defines the default public chat template and optional LuckPerms group format overrides.
  • Controls PlaceholderAPI expansion in trusted templates, public chat cooldowns, private-message cooldowns, mention formatting, and player-authored legacy color/style permission behavior.
  • Provides the fallback visual format used when a channel does not define its own format.

Important notes:

  • Server templates are trusted and may use MiniMessage. Raw player messages are sanitized and filtered before rendering.
  • Group format keys match the LuckPerms primary group in lowercase and are used only when the active channel does not override the format.
  • The formatting.permissions section controls player-authored message codes, not administrator-written config templates.
  • Public chat and private-message cooldowns are separate. Permission bypass nodes are declared in plugin.yml.

channels.yml

Channel definitions, scopes, send/receive permissions, source-specific mentions, ChatItems, bubbles, and bridge export rules.

Purpose:

  • Defines named chat channels, their aliases, scopes, default channel, formats, permissions, mention behavior, ChatItem behavior, chat bubble behavior, and bridge export behavior.
  • Controls whether a channel is backend-local, network-routed, or staff-only.
  • Allows separate mention rules for Minecraft-origin, Discord-origin, and Telegram-origin messages.

Important behavior:

  • scope: NETWORK can cross Paper backend boundaries only when the backend is in proxy mode and Velocity routing is active.
  • With Velocity multi-channel groups, network channel messages stay inside the sender CoreChatX channel group.
  • allow-mentions.from-discord and allow-mentions.from-telegram prevent external bridges from automatically gaining the same mention power as Minecraft chat.
  • export-to-bridges must be true before Discord or Telegram outbound relays use that CoreChatX channel.

  global:

Velocity Properties

Velocity uses a properties file rather than YAML. It is included here because it is required for proxy groups and network routing.

velocity-config.properties

Velocity-side proxy routing config. network-channel accepts one value or a comma-separated list of isolated CoreChatX groups.

Purpose:

  • Registers one or more CoreChatX plugin messaging channels on the proxy.
  • Creates one isolated Velocity router per configured channel.
  • Controls whether group player names are added to chat completions and TAB entries where Velocity exposes them.

Important rules:

  • Legacy format remains valid: network-channel=corechatx:main.
  • Multi-group format is comma-separated: network-channel=corechatx:survival,corechatx:minigames.
  • The group is the channel itself. There is no separate servers= list.
  • A Paper backend joins the group matching its own deployment.network-channel.
  • Private messages search only the sender group. They do not search proxy-wide.
  • Invalid channel values are skipped with warnings. If none are valid, Velocity routing is disabled.
  • Changing this file requires a Velocity restart.

Current bundled default:

# CoreChatX Velocity proxy settings.
# Comma-separate values to split this proxy into isolated CoreChatX network groups.
# Each Paper backend joins the group matching its deployment.network-channel.
network-channel=corechatx:main

# Adds group player names and @names to client chat completions.
player-directory.chat-completions=true

# Adds group online players to TAB where Velocity exposes them.
player-directory.tab-entries=true

Runtime Data Files

Some files are generated by live server activity and are not bundled as full default templates. Do not paste example data over live files unless you are deliberately resetting state.

  • channeldata.yml: generated active channel state.
  • ignoredata.yml: generated ignore state.
  • mutedata.yml: generated mute state.
  • discordlinks.yml: generated Discord account-link mappings between Minecraft UUIDs and Discord user ids.
  • playerdata.yml: bundled as an empty root, then populated with player settings such as PM toggle, ping toggles, social spy, locale, bubble preference, and nickname.
  • state.yml: bundled initial global state.

Config-driven Permissions

Most fixed command and feature permissions are declared in plugin.yml. Some feature permissions also come from config values so admins can choose their own nodes.

  • channels.yml can define per-channel send/receive permissions.
  • pings.yml can define custom ping receiver permissions.
  • privacy.yml, moderation.yml, chatitems.yml, and chat.yml expose behavior-specific permission nodes.
  • /nick uses fixed command permissions plus fixed granular color/style child permissions from plugin.yml.
  • /discord link commands use fixed command permissions from plugin.yml.
  • Use LuckPerms or another permission plugin as the source of truth for assignments.

Practical Admin Notes

  • Treat deployment.* and Velocity network-channel as boot identity, not casual reload settings.
  • Keep one source of truth for each visual decision. Avoid letting multiple chat plugins format the same message.
  • Use CoreChatX channels for routing rules instead of hardcoding bridge behavior in several places.
  • Back up discordlinks.yml with the rest of the runtime data if account linking is enabled.
  • Use PlaceholderAPI in trusted templates, not as a way to let players execute arbitrary placeholder expansion through raw chat.
  • Back up runtime data files before manual edits. Runtime data is user/plugin state, not a sample config.

Troubleshooting Quick Reference

Network messages do not cross servers

  • Verify the Paper backend uses deployment.mode: "PROXY".
  • Verify deployment.network-features-allowed: true.
  • Verify Paper deployment.network-channel is present in Velocity network-channel.
  • Verify the Velocity jar is installed and has been restarted after channel list changes.
  • In multi-group mode, verify the sender and target backend are intentionally on the same channel group.

Private messages cannot find a player on another server

PM lookup is group-local by design. The target must be inside the same CoreChatX proxy group as the sender. Different Velocity channel groups are intentionally isolated.

Join/leave messages are duplicated or missing

  • Use join-quit.mode: "LOCAL" for backend-local behavior.
  • Use join-quit.mode: "NETWORK" only when the Paper backend participates in proxy mode and Velocity routing is available.
  • Server switches inside one group suppress fake leave/join announcements; switches between groups announce leave in the old group and join in the new group.

Nicknames reject a shortened name

Check nicknames.change-only-colors. When true, CoreChatX accepts only color/style changes around the real Minecraft username.

Nickname colors or styles disappear

Check the sender's permissions. Without the relevant child permission, CoreChatX strips that legacy code or safe MiniMessage tag from the stored nickname. Hex and gradients require corechatx.nick.color.hex and corechatx.nick.color.gradient.

Nickname does not sync to another backend

  • Verify Paper and Velocity are both running the same current release.
  • Verify both backends are in the same CoreChatX Velocity channel group.
  • Verify another online player is available on the receiving backend, because plugin messages need a carrier.

Discord or Telegram messages do not send

  • Verify deployment.bridges-allowed: true.
  • Verify the specific bridge config is enabled.
  • Verify the CoreChatX channel has export-to-bridges: true.
  • Keep private tokens out of public logs and support screenshots.

Discord users cannot write into Minecraft channels

  • Check discord.inbound.account-linking.enabled and require-linked.
  • Check route overrides in discord.yml and channel overrides in channels.yml.
  • If linked users are blocked, verify Minecraft mute state and channel send permission requirements.
  • If unlinked messages are not deleted, verify the bot has Discord's Manage Messages permission.

Players are kicked with a Discord link code

discord.inbound.account-linking.require-linked-to-play is enabled and the Discord inbound bridge is available. The player must use the Discord slash command shown in the kick reason before joining normally.

If this setting is enabled but players are not kicked, check deployment.bridges-allowed, discord.enabled, discord.inbound.enabled, the bot token, and whether the bot is in a Discord guild. CoreChatX intentionally skips enforcement when slash commands are unavailable so players are not locked out with an unusable code.

PlaceholderAPI placeholders do not render

  • Verify PlaceholderAPI is installed on the Paper backend.
  • Verify hooks.placeholderapi: true.
  • Verify the specific config area supports PlaceholderAPI expansion.
  • Reload after changing trusted templates; restart only if changing deployment identity.

ChatItems work locally but not across servers

  • Verify proxy mode and network features are enabled.
  • Verify both backends are in the same CoreChatX Velocity channel group.
  • Check chatitems.yml expiry and network snapshot limits.
  • Check that the player has the relevant ChatItem permission.

A runtime data file looks wrong

Stop the server, back up the file, then inspect it. Runtime files such as playerdata.yml, channeldata.yml, ignoredata.yml, and mutedata.yml are live state. Deleting or editing them changes player/plugin data.

Production Validation Checklist

Before opening a server to players:

  • Start one Paper backend and confirm the CoreChatX startup banner and deployment summary.
  • Run /corechatx reload after a harmless wording change and confirm it applies.
  • Test public chat, one channel switch, one PM, one ignore, one PM toggle, and one ping toggle.
  • Test /nick with allowed and disallowed color/style permissions.
  • If using proxy mode, test network chat, same-group PM, cross-group PM rejection, state sync, ChatItem snapshot click, and network join/leave.
  • If using bridges, test outbound and inbound Discord/Telegram routes only after tokens and channel ids are configured privately.
