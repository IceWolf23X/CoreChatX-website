Purpose:#

  • declare one or more plugin messaging channels used as isolated CoreChatX groups
  • control proxy-provided group player chat completions and TAB entries
  • control Velocity update checks and the optional PremiumVanish announcement hook
  • document where proxy-owned runtime data is stored
  • authorize Velocity backend names for CoreChatX groups, including mandatory pins in multi-group deployments

Current bundled default:#

Important rules:#

  • each listed network-channel value creates a separate CoreChatX group
  • with one configured group, participating backends can register without backend-groups entries
  • with multiple groups, every participating backend requires backend-groups.<velocity-server-name>=<network-channel> for ordinary routing as well as pre-backend account-linking and role gates
  • each Paper backend's deployment.network-channel must match its proxy-authorized group; a backend cannot select or move itself to another group through Paper configuration
  • each Paper deployment.server-id must equal its registered Velocity backend name, case-insensitively, so protocol replies return to the correct backend
  • unmapped or wrong-group backends are excluded from CoreChatX routing in multi-group mode; invalid, ambiguous, or conflicting mappings leave routing unavailable instead of selecting a fallback group
  • changing this file requires a Velocity restart
  • changing network-channel also requires restart on affected backends after their deployment.network-channel is aligned
  • CoreChatX 2026.3.2 uses plugin-message protocol 30; Velocity and all participating Paper backends must run matching current builds because protocol 29 and older packets are rejected
  • Velocity startup prints the same CORECHATX banner shape with version, author, Velocity architecture, and project-link placeholder
  • if invalid, the proxy logs degraded routing state instead of silently pretending everything is fine
  • the same lowercase namespaced-key validation used by Paper is applied here
  • Velocity uses the real current backend connection as the source of live player actions; packets claiming an offline player or a player hosted on another backend are rejected
  • player-directory.chat-completions: false leaves client chat completions untouched by CoreChatX
  • player-directory.tab-entries: false leaves client TAB entries untouched by CoreChatX
  • update-check.enabled defaults to true; Velocity reports updates in console only, after startup and every update-check.interval-hours hours, clamped to 1..168
  • hooks.premiumvanish defaults to true but activates only when PremiumVanish is installed on Velocity; it suppresses hidden-player network join, first-join, quit, and matching bridge announcements
  • Velocity verifies all 16 external runtime JARs in plugins/corechatx/libs/ against the byte lengths and SHA-256 digests bundled in META-INF/corechatx/velocity-libraries.lock. A missing lock, corrupt cache/download, or unsafe path blocks runtime startup; stop the proxy and inspect the reported file, then retry with a trusted CoreChatX build
  • runtime-library verification has no configuration bypass and does not trust a checksum supplied by the download source
  • in PROXY, Velocity owns runtime data under data/groups/<encoded-channel>/ with YAML or in isolated database scopes with MySQL; Paper runtime YAML files are not the authority for cross-server state
  • in PROXY, Discord bridge I/O, account-linking and required-play role checks are configured in Velocity velocity-discord.yml; there is no backend authority-server carrier requirement
