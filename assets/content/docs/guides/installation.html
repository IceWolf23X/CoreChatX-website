Complete installation guide

Install CoreChatX on one server or a Velocity network.

Choose the setup that matches your server, place the correct jar files, generate the default configuration, and test the features you enable.

Download CoreChatX Open configuration reference

1. Choose a mode

Choose between one Paper server and a Velocity network.

Make this choice before configuring channels, Discord, Telegram, or player settings. It decides where CoreChatX saves shared data and whether messages can cross servers.

DecisionStandalone PaperPaper + Velocity
Best forOne Paper serverMultiple Paper servers behind one Velocity proxy
Where to installPaper onlyEvery Paper server and the Velocity proxy
Channel reachAll channels stay on this serverNETWORK channels can cross Paper servers in the same group
Private messagesLocal playersCross-server inside the same CoreChatX group
Where shared player settings are savedOn PaperOn Velocity, separated by network group
Where to configure DiscordPaperVelocity for chat, linking, and Discord role requirements
Where to configure TelegramPaperOn the Paper server that sends the message

On a standalone server, a NETWORK channel behaves like a normal local channel. You need Velocity only when chat or player settings must work across multiple Paper servers.

4. First startup

Start once to create the default files.

  1. Stop the target Paper server or Velocity proxy cleanly.
  2. Copy the correct CoreChatX jar into that server or proxy's plugins/ folder.
  3. Start the server or proxy once.
  4. Confirm that startup prints the CORECHATX banner with the version and platform.
  5. Confirm that the expected CoreChatX data folder and default files were created.
  6. Stop the server or proxy before changing the mode, server ID, network group, or Velocity configuration.
  7. Apply the standalone or Velocity instructions below, then restart.

If the banner does not appear, check that you downloaded the correct jar, placed it in the right folder, and are using the Java version required by that server release. Then read the startup log for the error.

5A. Standalone Paper

Use this setup for one Paper server.

  1. Install only the Paper JAR.
  2. Open plugins/CoreChatX/config.yml.
  3. Keep deployment.mode set to STANDALONE.
  4. Give the Paper server a stable server-id.
  5. Keep network-features-allowed disabled.
  6. Keep bridges-allowed enabled only if you plan to use Discord or Telegram.
  7. Restart after changing the deployment block.
  8. Configure formats, channels, privacy, moderation, interactive features, languages, and optional integrations.
YAML
deployment:
  mode: "STANDALONE"
  server-id: "paper-1"
  network-channel: "corechatx:main"
  bridges-allowed: true
  network-features-allowed: false

Paper saves player settings, channels, ignores, mutes, nicknames, and linked Discord accounts in YAML by default. For MySQL, configure storage.yml; existing data needs the migration workflow. Cross-server features remain disabled without Velocity.

Test the standalone setup

  • Public chat renders with the expected format.
  • A channel switch changes the active local channel.
  • Private messages, reply settings, player preferences, nicknames, and moderation data remain saved after a normal restart.
  • Any enabled Discord or Telegram connection sends and receives through the intended local channel.

5B. Velocity network

Choose which Paper servers should share chat and settings.

Each Paper server joins one CoreChatX group through deployment.network-channel. Servers in the same group share supported chat features and player settings. Servers in different groups remain separate.

Write down each server and its group

Server name in VelocityUnique CoreChatX server IDCoreChatX group
lobbylobbycorechatx:main
survival-asurvival-acorechatx:survival
survival-bsurvival-bcorechatx:survival

Every server-id must be unique and must match that server's registered Velocity backend name, case-insensitively. Protocol 30 uses this identity to correlate authoritative requests and replies.

Configure every Paper server in the network

YAML
deployment:
  mode: "PROXY"
  server-id: "survival-a"
  network-channel: "corechatx:survival"
  bridges-allowed: true
  network-features-allowed: true
  1. Install the Paper jar on every Paper server that should participate.
  2. Set mode to PROXY.
  3. Assign a unique, stable server-id matching the registered Velocity backend name.
  4. Set the exact CoreChatX group in network-channel.
  5. Enable network-features-allowed.

Configure the Velocity proxy

Properties
# Comma-separate every allowed CoreChatX group.
network-channel=corechatx:main,corechatx:survival

# Required for every participating backend when multiple groups are configured.
backend-groups.lobby=corechatx:main
backend-groups.survival-a=corechatx:survival
backend-groups.survival-b=corechatx:survival

player-directory.chat-completions=true
player-directory.tab-entries=true

The backend-groups entries are optional only when exactly one CoreChatX group is configured. With multiple groups, map every participating backend; unmapped or wrong-group traffic is rejected. The mappings also enable pre-backend Discord admission and individual backend monitoring.

Restart and test the network

  1. Restart Velocity after every proxy configuration change.
  2. Restart affected Paper servers after changing mode, server ID, or network channel.
  3. Connect at least one test player to each relevant Paper server.
  4. Send one eligible NETWORK channel message in both directions.
  5. Test one cross-server PM and one remote ChatItem preview.
  6. Switch between Paper servers and confirm that settings, nickname, privacy choices, and the active channel follow the player.

The network-channel value must be exactly the same on Paper and Velocity. The chat channel must also use scope: NETWORK before messages can cross servers.

Discord and Telegram checklist

  • Keep deployment.bridges-allowed enabled on the relevant Paper server.
  • Enable only the Discord or Telegram features you intend to use.
  • Enable outbound export only on CoreChatX channels that should leave Minecraft.
  • Map inbound traffic to an existing CoreChatX channel.
  • Telegram accepts inbound messages only from explicitly configured chat/topic routes by default; enable allow-unmapped-chats only when the legacy fallback is intentional.
  • Telegram and other generic remote sources can activate only custom pings whose use-permission is blank.
  • Keep tokens out of screenshots, public logs, public posts, and support messages.
  • Enable the Discord Message Content intent when inbound message content is required.
  • Enable the privileged Server Members Intent when linked-role admission is used.

Discord and Telegram URLs shown in configuration examples are non-clickable placeholders for your own server setup.

7. Optional advancement synchronization

Plan this feature as a coordinated Velocity deployment.

Full advancement synchronization is optional and disabled by default. It shares criteria, partial progress, completion dates, and revocations only between Paper backends in the same CoreChatX Velocity group. It requires matching 2026.3.2 builds, explicit Velocity backend-to-group pins, a unique credential per backend, and a restart after configuration.

Back up each affected CoreChatX plugin folder, complete Minecraft worlds, and the CoreChatX database when MySQL is used before enabling this option. Install the matching Paper and Velocity JARs, start Velocity first, then use the dedicated setup guide to configure and test one group before regular play.

Open advancement synchronization setup

Optional network death messages

Death-message relay is a separate, disabled-by-default feature. Run matching Paper and Velocity builds, use PROXY mode with network features enabled, align backend identity and group mapping, then enable death-messages.network-enabled on every participating Paper backend and reload each backend. The switch controls both sending and receiving. Only unrestricted public death components are relayed; cancelled, hidden, team-restricted, private, or empty messages remain local, and there is no history or replay for an unavailable backend. See the complete death-message setup and limits.

8. Existing installations

Upgrade the whole network and preserve authoritative data.

To 2026.3.2

  1. Stop the affected servers; on a network, stop Paper backends before Velocity so final saves can finish. Back up every file and subfolder in the CoreChatX plugin folders, complete Minecraft worlds, and MySQL when used.
  2. Download the 2026.3.2 release from Modrinth.
  3. Replace the CoreChatX JAR on Velocity and each participating Paper backend with the matching 2026.3.2 JAR. Keep only one CoreChatX JAR per server and leave configuration, runtime files, database and journals intact.
  4. Before boot, make every Paper deployment.server-id match its Velocity backend name and, for multiple groups, map every participating backend in backend-groups.*.
  5. Review Telegram inbound routes. Unmapped chats/topics are now denied by default; add explicit routes or deliberately set telegram.inbound.allow-unmapped-chats: true to retain the previous fallback.
  6. Start Velocity first, then its Paper backends; for standalone, start Paper. Verify that the startup banner shows 2026.3.2, then check chat and player settings.

CoreChatX 2026.3.2 uses plugin-message protocol 30; protocol-29 and older JARs are rejected, so mixed 2026.3.1/2026.3.2 networks are incompatible. Upgrading from 2026.3.1 adds no database migration. V004 remains required because it was introduced by 2026.3.1, even when advancement synchronization stays disabled.

From 2026.2.6 or earlier

  1. Stop the affected servers and back up plugin configuration, complete worlds, live YAML or database data, and any storage journals.
  2. Replace Paper and Velocity JARs together with matching 2026.3.2 builds. Protocol-29 and older builds cannot remain in a mixed network.
  3. Align each proxy-mode server-id with its Velocity backend name and complete every required multi-group mapping before startup.
  4. Keep YAML if you do not need a database. Legacy storage.sql.* settings do not enable MySQL.
  5. For existing YAML-to-MySQL data, configure connection settings and use the confirmed /ccxstorage plan/execute workflow. Change the backend only when instructed, then restart.
  6. Schema V004 adds advancement records for MySQL and applies even with synchronization disabled. With schema-auto-migrate: false, arrange the schema upgrade before startup. Older builds reject schema 4.
  7. For MySQL-to-YAML rollback, export the latest database data through the rollback workflow; do not replace it with a stale pre-migration archive.
  8. Review Telegram inbound routes and custom ping permissions before enabling the bridge.

Only recreate individual configuration files when needed. Preserve storage.yml or velocity-storage.yml and restore the active backend/identity before booting; their defaults select YAML. Never remove player data or transition journals as configuration cleanup.

Back up the complete plugin folders and rehearse migration and rollback with an isolated copy of your own data before opening the server. Follow the preparation checks and the YAML to MySQL guide, then review the complete release notes.

11. Production validation

Test the features you enabled before players join.

Installation and chat

  • Confirm the CORECHATX banner on every Paper server and on Velocity, if used.
  • Send normal public chat and verify the expected format.
  • Switch channels and test both send and receive permissions.
  • Test a shortcut in switch mode and one-shot send mode.
  • Test permanent and timed /hidechannel, followed by /unhidechannel.
  • Test /msg, /reply, disconnect one participant, and confirm the old reply target is cleared.
  • Test nickname, real-name lookup, locale, player settings, ignore behavior, and moderation.

Interactive features and Velocity

  • Test one PlaceholderAPI value in a trusted template.
  • Test mentions, custom pings, notification toggles, and one interactive keyword.
  • Open one local ChatItem preview.
  • In proxy mode, test a network channel message from each Paper server, one cross-server private message, and one remote ChatItem preview.
  • Switch a test player between Paper servers and verify that their settings follow them.

Discord and Telegram, if enabled

  • Test messages from Minecraft to Discord or Telegram and back for every configured channel.
  • Test Discord linking, unlinking, nickname synchronization, player lists, event mirrors, descriptions, and status messages that you enabled.
  • If role admission is active, remove the final allowed role and confirm disconnect plus blocked reconnect.
  • Test Telegram messages in both directions and any configured forum topics.
  • If Discord ChatItem images are enabled, test an image and its item-inspection selector.

Reload check

Change one harmless message, run /corechatx reload, and confirm that the new wording appears.

Network message missing? Check PROXY mode, unique server IDs, enabled network features, exactly matching group values, a channel using scope: NETWORK, the CoreChatX Velocity jar, and at least one connected test player.
